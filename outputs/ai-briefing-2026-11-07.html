Claude Code がアカウントのメールアドレスを Web リクエストの User-Agent に載せていた問題——v2.1.317 以降は遮断用の内蔵 mod が既定で有効、ただし抜け穴の報告が続く

DEVCONSULTPM

GitHub の公式リポジトリで11月5日に起票された Issue #107757（v2.1.318・macOS）は、Claude Code が Web 検索時の HTTP リクエストの User-Agent ヘッダーにアカウントのメールアドレスを入れ、第三者のサイトに送っていると報告した。起票者は迷惑メールが1日数十通届くと述べ、設定ではなく機能自体の削除を求めている。コメント欄では、Anthropic 側の貢献者が v2.1.317 で追加した内蔵 mod「cc-plugin-privacy」が該当の挙動を決定論的に止めると説明した（既定で有効、/plugins で無効化可能）。一方11月6日には別の利用者が、モデルが自作の curl や Python スクリプトで User-Agent を組み立てる際にプロジェクト名や顧客名、メールアドレスを入れる例を報告し、mod はアカウントのメールだけを照合するためファイル経由・メールなしの記述は通ると指摘した。Issue は執筆時点で未解決である。

  • DEV自分の環境で内蔵 mod が有効か（/plugins）を確認し、エージェントが生成するスクリプトの User-Agent やヘッダーに識別情報が入っていないかをレビュー項目に加えられる。
  • CONSULT顧客案件で AI エージェントに外部アクセスさせる場合、「エージェントが送信先に何を付けるか」を情報漏えい経路として説明・確認する材料になる（個人情報の取扱いの観点）。
  • PMエージェント利用の標準ルールに、外部通信のログ確認とバージョン更新の運用（最新版へ上げる担当・頻度）を入れる根拠になる。
どう試す／どう対応する：Claude Code を最新版に更新し、/plugins で cc-plugin-privacy が無効になっていないことを確認する。顧客案件では外部通信の許可先を絞り、エージェント作成スクリプトの送信ヘッダーを一度目視する。

Anthropic Engineering が「エージェントの記憶」の構成要素を整理——注入する最上層は小さく保ち、記憶を定期的に見直す「dreaming」で wiki 検索の正答率が13%→48%

DEVPM

Anthropic Engineering は11月6日、記憶を「セッションをまたいで保持される経験由来の知識」と定義し（重み更新・文脈内学習・圧縮は除外）、5層で説明した。会話の記録（transcripts）、記憶ノート、wiki 形式などの表現、毎回読み込む注入文脈、そしてオフラインで記録とノートを見直して誤りを直し最上層を更新する dreaming である。推奨は、記憶の目的を伝えるが使い方は細かく指定しない、最上層は小さくし詳細は下層にリンクで置く、画面から読める状態は保存しない、wiki は担当ごとにページを分けて重要語は原文のまま引用する、など。実測では CL-Bench の DB タスクで Opus 5.5 が平均報酬0.655→0.838、Stainless の文書25問で wiki 単独の正答率が128回の dreaming で13%→48%、wiki＋検索は61%（検索単独53%）で1問あたり約2万トークン節約と報告している。

  • DEVCLAUDE.md や記憶ファイルを「常時読み込む少量の核」と「必要時に辿る下層」に分け、定期的に記録と照合して誤りを直す運用を設計に組み込める。
  • PM記憶は放置すると誤りが信頼されて残るので、棚卸しの担当と頻度を運用計画に入れる根拠になる。トークン節約の数値も費用見積りの参考になる。

AWS Japan ブログ（11月6日付）は、Kiro Crew で Bot の一般提供が11月5日に始まったと紹介した。Bot は名前とアバターを持ち、1つのチャットを継続して使い、ゴールに向けて自分から動く。Bot ごとにメモリと作業ログを持ち、ワーカーエージェントのセッションを並行起動して計画から外れたものを修正し、結果を1つのチャットにまとめる。定期実行（夜間ビルドの確認や週次リリースノート作成）、Bot ごとのダッシュボード、Bot とワーカーでのモデル使い分けにも対応する。統制面では、調査用 Bot は読み取りと Web 検索のみ、デプロイ用 Bot は変更前に承認を求める、レビュー用 Bot はコメントはできても承認・マージはできない、といった設計が可能で、Bot がツール追加を依頼しても承認するまで権限は変わらない。記憶は表示・編集・削除できる。料金は記事に記載がない。

  • DEVBot ごとに権限・メモリ・モデルを分ける設計は、自作のエージェント基盤でも「役割ごとの最小権限」の型として参照できる。
  • PMレビュー Bot が承認やマージをできない設計は、AI の判断と人の承認を工程で分ける実例で、運用ルール作りに使える。
  • CONSULTAWS がチーム常駐型エージェントを製品化した事例として、クライアントの AWS 前提の開発体制提案で比較材料になる。
