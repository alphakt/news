Google が「Gemini Decisions API」を公開——文章を生成せず、選択肢ごとの確率だけを150〜250ミリ秒で返す。入力100万トークン0.10ドル、出力は無料

DEVPMCONSULT

Google は11月11日、ツール選択、ポリシー判定、モデルのルーティング、文脈の採点といった「閉じた選択肢の判断」に特化した API を発表した。モデルは Gemini Decision 1。テキスト・画像・音声・動画・PDF を含む最大256Kトークンの共通入力に対し、1リクエストで最大1,000個の質問を投げられる。質問の型は真偽（noul）、2〜255択の選択（choice）、順序尺度の採点（score）の3種で、回答文は生成せず確率と0〜1の確信度だけを返す。遅延は端から端まで150〜250ミリ秒で、質問数を1から100に増やしてもほぼ変わらないという。Google 自身も Gemini Notebook のモデル振り分け（日常的な質問で遅延最大40%減）や、Google 検索の MCP ツール向け安全層に使っている。AI Studio で API キーを取って試せ、OpenRouter、LangChain、LiteLLM などの対応も順次進む。Google Cloud（Vertex AI）での提供は「近日」。

  • DEVエージェントの小さな判断（どのツールを呼ぶか、止めるか、危険か）を主モデルから外す構成が、主要クラウド各社の API で組めるようになった。
  • PM出力課金ゼロ・共通入力は1回課金なので、高頻度の分類・判定処理の単価見積もりを作り直す価値がある。
  • CONSULTOpenAI、Amazon（Strands Decider）に続き Google も参入し、「判断は専用モデル」が業界の型になった。顧客のコスト削減提案の定番メニューに入れられる。
どう試す／どう対応する：AI Studio の無料枠で、既存の LLM 呼び出しのうち「出力がラベル1語」の処理を1つ選び、同じ入力で Decisions API と現行モデルの一致率・遅延を比べる。
出典：Google Blog「Gemini Decisions API: Fast, calibrated multimodal decisions」（2026-11-11）
精度・費用の比較（Gemini 3.5 Flash-Lite 比で約5分の1の費用など）は Google 自身のベンチマークによる。プレビューか GA か、対応リージョンは発表に記載なし。
コメント：決定モデルは「面白い研究」から「大手3社が値札を付けて売る部品」に変わった。

Claude に共同編集の「Sheets」「Whiteboards」と、ダッシュボード機能の正式版「Claude Data」が登場——Enterprise プランでは Claude Data が11月19日に既定で有効化

CONSULTPM

Anthropic は11月10日、Claude の成果物機能を拡張した。Whiteboards（β）はチームで Claude とブレインストーミングする共有ボードで、話した計画を担当者・期日付きのボードに変換できる。Sheets（β）は数式・書式・プルダウン付きの表を生成し、各編集の内容を示して追跡できる。従来の Claude Dashboards は「Claude Data」として正式提供となり、データ部門が指標の定義を「認定」すると、グラフに認定バッジが付き、共有先には承認済みクエリだけが見える（認定クエリとライブ共有はβ）。Adobe、Atlassian、Box、Notion などは会話の横でアプリとして開けるようになった。全有料プランで Web・デスクトップ・モバイルに提供。管理設定は、Team プランでは3機能とも既定で有効、Enterprise プランでは Whiteboards と Sheets は既定で無効、Claude Data は11月19日に既定で有効になる。

Kiro に「Approve for me」——規則で決まらない操作を LLM が審査し、安全なら自動実行、危険なら阻止、迷うものだけ人に聞く。社内計測では審査対象の約97%が確認なしで実行

DEVPM

Kiro は11月10日、エージェントの操作承認を減らす機能を Kiro IDE・CLI・Web に追加した。まず従来の許可規則（allow／ask／deny）が適用され、規則に当たらない操作だけを LLM（現在は Anthropic のモデル）が審査する。結果は「安全なら実行」「危険なら阻止」「不確かなら人に確認」の3つで、3回連続で阻止されると理由付きで人に戻す。社内の1週間のサンプルでは、CLI のツール呼び出しの15.8%で確認を求め、その97.1%を利用者が承認していた。新機能では約7割が規則で処理され、約3割が審査に回り、そのうち約97%は確認なし、約2%が人へ、1%未満が阻止。審査の中央値は1秒未満。既定は無効で、有料ユーザー向け（us-east-1、eu-central-1）。審査分は利用枠を消費する。

  • DEV「全部許可」と「毎回確認」の間に、規則＋LLM 審査という第3の選択肢ができた。ただしシェルコマンド実行後のアクセス範囲は制限しないので、ローカルサンドボックスと併用が前提。
  • PM「確認の97%は承認されるだけ」という数字は、承認作業が形骸化している証拠。チームの権限規則（deny を何にするか）を先に整える価値がある。
どう試す／どう対応する：Kiro IDE 1.4.154 以上／CLI 2.36 以上に更新し、チャット入力メニューから有効化。まず deny 規則（本番接続、秘密情報、push など）を書いてから試す。
出典：Kiro Blog「Introducing 'Approve for me' in Kiro」（2026-11-10）
数値は Kiro の社内計測。審査判断のログ・監査証跡の扱いは記事に記載なし。
コメント：人の承認を「規則で決まらない残り」に絞るという設計で、決定モデル的な発想が権限管理に入ってきた。
重要度：高

「AI がコードを書くなら、テストはコードでなく“データ”で持て」——martinfowler.com が、エージェントに書き換えられにくい顧客テストの作り方を具体例付きで公開

DEVPM

Thoughtworks の Matteo Vaccari は11月11日、AI が書くテストは読みにくく、実装に密結合し、ときにバグをそのまま正とする、と問題提起した。提案は、AI がコードを書くなら開発者は「顧客」になるので、人と AI の契約は開発者テストではなく顧客テストにし、それをテストコードではなく YAML・CSV・表などのデータで持つこと。入力・前提・期待結果だけを書き、パーサーとテストランナーは AI に書かせる。人は最初のサンプルを書いて結果をレビューし、AI はそれを型に事例を増やす。DSL の文法で検証項目を必須にして弱い確認を書けなくする、テストデータのファイルを読み取り専用や CI の変更チェックで守る、公式ドキュメントや別実装を基準にテスト自体を検証する、といった実践も挙げる。COBOL インタプリタの例では、実機 IBM i と照合している。

  • DEVエージェントに「テストを通すためにテストを直す」余地を与えない具体策。テストデータのファイルを変更禁止にするだけでも今日からできる。
  • PM人のレビューを「コード全行」から「表形式の期待結果」に移せるので、AI 生成 PR のレビュー負荷と品質保証の分担を設計し直す材料になる。
どう試す／どう対応する：既存の判定ロジック（権限、料金計算など）を1つ選び、入力と期待結果を CSV にしてエージェントにランナーを書かせる。その CSV を CLAUDE.md／AGENTS.md で「編集禁止」と明記し、CI でも変更を検知する。
出典：martinfowler.com「Tests as data: ensuring AI-generated code does what we want」（2026-11-11）
コメント：レガシー移行（旧新システムに同じテストデータを流す）にもそのまま使え、SIer 案件との相性が良い。
重要度：中

AWS が「Nitro Sandboxes」を提供開始——EC2 上でハードウェア分離の軽量 VM を追加料金なしで動かし、AI エージェントが生成したコードの実行先に。EKS・ECS ではポッド／タスク単位で隔離

DEVCONSULT

AWS は Nitro Sandboxes を発表した（AWS ジャパンブログの EKS 向け記事は11月10日）。親となる EC2 インスタンスの vCPU とメモリを使い、Nitro ハイパーバイザー上で親と並んで動く軽量 VM で、ワークロード同士や親インスタンスのメモリから分離される。用途としてドキュメントは「利用者のコードを実行する AI エージェント」「別テナントのワークロード」「ビルドジョブ」を挙げる。EKS では各ポッド、ECS では各タスクを個別のサンドボックスで動かせ、自前の環境では Firecracker で起動する。親からもメモリを読めない機密モード（既定、暗号学的な証明付き）と、親とメモリを共有する直接モードを選べる。追加料金はなく、親インスタンス 1vCPU あたり最大5個、1台で最大896個まで。GPU のパススルーは未対応。

  • DEVコンテナはカーネルを共有するため、エージェントに任意コードを実行させる環境の隔離境界を VM 単位に上げる選択肢が、既存の EKS 運用のまま取れるようになった。
  • CONSULT「エージェントの実行環境は安全か」という顧客の問いに、AWS 標準機能で答えられる。Lambda MicroVMs、Nitro Enclaves との使い分けがドキュメントに整理されている。
出典：Amazon EC2 ユーザーガイド「Isolate workloads with AWS Nitro Sandboxes」AWS ジャパンブログ「AWS Nitro Sandboxes: Amazon EKS で実現するハードウェア強制型ワークロード分離」（2026-11-10）
注意点としてドキュメントは、親が NAT で通信を中継すると、サンドボックスから親の IMDS（IAM 認証情報）に届くため 169.254.169.254 宛を拒否すべきと明記している。
コメント：エージェント実行基盤の「サンドボックス」がクラウドの標準部品になりつつあり、自前で作る理由が減っている。
重要度：中

「トークン消費量は AI 時代のコード行数か？」——JetBrains の技術者404人・5週間のデータでは、消費量は成果をほとんど表さず「使った量」を表すだけ

PMCONSULT

11月10日に arXiv に投稿された論文は、JetBrains の技術者404人のコーディングエージェントのトークン消費を5週間分、コミットと結び付けて分析し、412人への社内調査と合わせて検討した。消費量の差は主に個人間の差で、多く使う人は期間を通じてほぼ同じ顔ぶれだった。コミット数が同程度の週同士でも、上位10%の消費量は下位10%の39〜240倍。同じ人の中では、消費を2倍にしてもコミットは約10%増えるだけだった。手元の作業指標で説明できたのは、個人間の差の38%、週ごとの変動の13%にとどまる。調査では、エージェントの用途は分析・調査・計画にも広く及んでいた。著者らは、トークン消費は「最大でも資源の会計」に使い、成果の評価には実際の作業内容と結果を使うべきだと結論づける。

  • PMトークン消費量をチームや個人の生産性指標・評価に使うのは避ける。費用管理の指標として予算と切り分けて扱う。
  • CONSULT顧客が「AI 活用度＝トークン消費量」のダッシュボードを作ろうとしていたら、この研究を根拠に成果指標の設計を提案できる。
出典：arXiv「The AI Era's Lines of Code? A Case Study on What an Engineer's Token Spend Measures」（2026-11-10 投稿）
査読前の論文。単一企業（JetBrains）のデータ。
コメント：「使った量で測る」誘惑に、実データで歯止めをかけてくれる貴重な研究。
重要度：中

コーディングエージェントは AGENTS.md の指示に従っているか——実在のコンテキストファイルの指示を検査スクリプトに変換して測ると、「おおむね従う」が、常に守られる指示と一度も守られない指示に二極化

DEV

11月10日に arXiv に投稿された研究は、実際のリポジトリにある AGENTS.md などのエージェント用コンテキストファイルと、それに紐づくエージェント作成のコミットを分析した。まずファイルに書かれた明示的で実行可能な指示を分類し、それぞれを自動で確認できる検査スクリプトに変換して、指示単位の遵守率を測った。観測できる指示の大半は検査可能な形に変換できた。エージェントは指示に「従わないより従うことの方が多い」が、遵守は二極化しており、毎回守られる指示がある一方で一度も守られない指示もある。遵守率は指示の種類とエージェントの種類によって異なる。著者らは、守られにくい種類の指示は書き方を変え、守らないエージェントにはコンテキストファイルの外での強制（フックや CI）を加えるべきだと提言する。

  • DEVCLAUDE.md／AGENTS.md の重要な指示は「書いたら守られる」前提にせず、検査スクリプトや CI で守られたかを確かめる仕組みとセットにする。
出典：arXiv「Do They Do as They Are Told? Investigating Coding Agents' Adherence to Explicit Instructions in Context Files」（2026-11-10 投稿）
査読前の論文。抄録時点ではエージェント名・指示の種類別の数値は未確認（本文参照）。
コメント：上の「テストをデータで持つ」と同じく、指示は書くだけでなく機械で検証する時代になった。

Thoughtworks の社内ハッカソンで作った AI 制御プレーン「Heimdall」——4週間・6人の試行で、有料 API に届くリクエストを63.6%削減し、個人情報の送信を4,170件止めた

PMDEV

Thoughtworks のブログ（11月10日）は、アプリや IDE 拡張と LLM 提供元の間に置くプロキシ型の制御プレーンを紹介した。OpenAI 互換の入口（ベース URL を変えるだけで導入）、Presidio などによる個人情報・認証情報の黒塗り（エラー時は止める fail-closed）、意味的キャッシュ、難易度に応じて最も安いモデルを選ぶルーター、チーム・モデル・期間ごとの予算（超過時は遮断せず Opus→Sonnet→Haiku→ローカルへ段階的に格下げ）、OpenTelemetry による可観測性の6部品で構成する。キャッシュ命中率は34.2%、追加遅延は約14ミリ秒。キャッシュのキーから IDE のメタデータを除くことが、アルゴリズム選びより効いたという。

  • PM「遮断ではなく格下げ」という予算超過時の振る舞いは、チームの AI 予算ルールを決める際の参考になる。
  • DEVゲートウェイの部品構成と、キャッシュキー正規化の知見はそのまま流用できる。
出典：Thoughtworks「We built an AI control plane to reduce LLM expenses and prevent data leaks」（2026-11-10）
6人・4週間のハッカソン試行で、金額ベースの削減率は示されていない。
コメント：規模は小さいが、AI 費用統制の「部品の並べ方」の見本として手元に置いておきたい。
