IPA が「AI時代の要求管理ハンドブック」Ver.1.0.0 を公開——AI の不確実性・データ品質・人と AI の役割分担を「要求」として書く方法を5部構成で整理

CONSULTPMDEV

IPA は11月5日、要求管理の考え方と実践方法をまとめたハンドブックを公開した。要望・要求・要件の違いといった基礎から始まり、AI 時代に要求管理がどう変わるか（AI システムの要求・要件、AI による要求管理支援）、モデリングとトレーサビリティ、法令・規制・社内規則を要件につなぐ考え方、組織への定着（役割分担・導入ステップ・成熟度・代表的な成果物）の全5部で構成される。要求は一度定義して終わりにせず、関係者の共通理解を作りながら変化に応じて継続的に管理するとし、AI の不確実性、データ品質、人と AI の役割分担を要求・要件として定義する点を扱う。読者は開発者に限らず、経営・事業部門、法務・調達、プロジェクト責任者まで想定され、全体を一律に適用せず役割や案件に応じて必要な部分を参照する前提である。

  • CONSULT日本の公的機関が出した共通の言葉なので、AI 案件の要件定義や提案書で「AI の不確実性・データ品質・役割分担をどう要求に落とすか」の拠り所として、クライアントに引用できる。
  • PM要求と設計・実装・評価・運用を関連付ける追跡可能性の章が、AI 案件の変更影響の把握や成熟度の自己診断の雛形になる。
  • DEVAI による要求の抽出・分析・整合性確認の支援にも触れており、仕様をエージェントに渡す前段の整理手順を見直す材料になる。
どう試す／どう対応する：進行中の AI 案件を1件選び、第2部「AI時代に要求管理はどう変わるか」と第5部の成熟度・成果物一覧を、現行の要件定義書と見比べて不足項目（AI の不確実性・データ品質・人と AI の分担）を洗い出す。

Thoughtworks が「エージェントの文脈腐敗（context rot）」の見分け方と5つの対処を公開——テスト出力はフィルタし、CLAUDE.md は定期的に棚卸しする

DEVPM

Thoughtworks は11月5日の記事で、文脈が長くなる・ノイズが増える・古くなることでモデルが文脈をうまく使えなくなる現象を context rot と定義した。症状は、前に決めた制約を無視する、失敗した方法を繰り返す、古い計画や最新のテスト結果を見落とす、無関係なファイルや巨大なツール出力に労力を使う、の5つ。対処は、ツール出力を次の判断に必要な分だけ渡す、長い作業は目標・制約・失敗した方法とその理由を要約する、必要になった時点で読み込む、AGENTS.md や CLAUDE.md の恒久ルールと一時的な作業状態を分ける、作業が大きく変わったら引き継ぎメモを付けて新しい文脈で始める、の5つである。トークン数ではなくタスク完了などの結果で評価することも勧めている。

  • DEVテスト実行後は失敗したテスト・エラー・関連スタックトレースだけを次の呼び出しに渡す設定と、CLAUDE.md の古い・矛盾する記述の定期削除を、今日から運用に入れられる。
  • PMエージェントが同じ失敗を繰り返す・終盤で品質が落ちるときは「文脈の問題」として切り分けられ、タスクの区切り方や引き継ぎメモの様式をチームの標準にできる。
どう試す／どう対応する：直近でエージェントが迷走した作業を1つ選び、その直前の文脈に何が入っていたかを確認する。巨大なツール出力があれば出力を絞り、CLAUDE.md の矛盾を消してから同じタスクを再実行して比べる。
出典：Thoughtworks「Context rot in AI agents」（2026-11-05）
実測値は示されていない。実践的な指針の記事。
コメント：11月4日・5日号のトークンとハーネスの話を、「何を渡さないか」という運用の言葉にまとめた一本で、手元の CLAUDE.md を読み直すきっかけになる。

トヨタ北米の SAP 運用基盤 BasisPilot：AI は68の型付きツールを「要求」するだけで、承認・RBAC・監査はアプリ側——カーネル更新は約2.5時間から約45分

CONSULTPMDEV

AWS Japan ブログ（11月5日）は、トヨタ北米が AWS 上の SAP 20システム・60台超の EC2 を1つのダッシュボードで運用する BasisPilot の構成を紹介した。Bedrock のツール使用でモデルは68種の型付きツールを要求でき、実行前にアプリが検証・RBAC 確認・承認を行う。AI が任意のシェルを実行することはなく、本番や破壊的操作は必ず承認待ちで、古い承認は失効する。作業前に AMI やバックアップを取り、完了はコマンドの受付ではなくライブの状態確認で判定し、全呼び出しをユーザー ID 付きで記録する。報告値は、運用情報の収集・分析時間が少なくとも約20%減、ステータス確認チケットが推定約25%減、カーネル更新が約2.5時間から約45分、ファイルシステム縮小が約3〜4時間から約1時間（いずれも観察件数に基づく報告値）。

  • CONSULT基幹システム運用への AI 導入で必ず出る「AI に勝手に操作させて大丈夫か」に対し、許可リスト・承認ゲート・巻き戻し・監査の具体的な設計例として示せる。
  • PM効果を「時間削減○%」と観察件数つきで測っており、AI 運用案件の効果測定の書き方と、承認待ちを工程に組み込む見積りの参考になる。
  • DEVモデルには「要求」だけをさせ、実行側で検証する構成は、エージェントの権限設計のそのまま使える型になる。
出典：AWS Japan Blog「トヨタはいかにして BasisPilot を構築したか」（2026-11-05）
効果の数値はトヨタ側の報告値でパイロットに基づく推定を含む。AWS の公式ブログである点に留意。

Bloomberg の大規模コード移行：2,333件の PR のうち成功は729件（約31%）——ボトルネックは生成ではなく、受け取るチームのレビュー・テスト・デプロイ

PMDEVCONSULT

arXiv（11月3日投稿）の Bloomberg の論文は、約1,900リポジトリの Python パッケージング移行と約6,700リポジトリの C++ ビルドシステム移行に、LLM と決定論的処理を組み合わせたパイプラインを使った結果を報告する。LLM は事前に計算した文脈内の限定的なファイル変換だけを担い、実行ログや利用トレースなど本番テレメトリも使う。PR は計2,333件、成功した移行は729件（約31%、掲載値からの計算）。著者らは、移行の生成は容易な部分で、主なボトルネックは所有チームがレビュー・テスト・デプロイする費用だと述べる。PR を出す前にパイプライン内で検証できる場合（C++ のコンパイルとテスト）と、リポジトリが均質で修正を横展開できる場合に費用が下がった。

  • PMAI による大規模移行の見積りでは「生成量」ではなく受け手側のレビュー工数と成功率（この例は約3割）を計画に入れる必要がある。
  • DEVPR を出す前に自動で検証する工程を作るほど、受け手の負担が下がることが示された。
  • CONSULTレガシー移行を AI で安く速くと提案する際、均質な対象から始める・事前検証を組み込む、という現実的な進め方の根拠にできる。
出典：arXiv:2611.05457「Hybrid LLM-Deterministic Pipelines for Enterprise-Scale Code Migration at Bloomberg」（2026-11-03）

Kiro Enterprise にクレジットプーリング：月$20・最小2シート・各500クレジットを組織で共有、追加は1クレジット$0.04、上限は3段階で設定

Kiro チームは11月4日、AWS Japan ブログは11月5日に、Kiro Enterprise でチーム全体のクレジットを1つの共有プールにまとめて使える機能を紹介した。シート料金は月額$20で最小2シート、各シートに毎月リセットされる500クレジットが含まれる。追加クレジットは1クレジット$0.04で購入直後にプールへ入り、最長12か月繰り越せる。消費順はシート分が先、次に追加購入分（期限の近いものから）。複数グループに所属する利用者でも支払いは1シート分で、利用上限はプロファイル・グループ・個人の3段階で設定でき、上限到達で追加購入まで利用がブロックされる。使用率80%と100%で管理者に通知が届く。第三者 ID プロバイダーによるグループ管理と管理 API は近日対応予定とされる。

  • PMパワーユーザーとライトユーザーの消費差を吸収でき、AI コーディング費用をシート単位ではなくプール＋上限で統制する具体例として、予算計画に使える。

GitHub が新しい Git ストレージ構成を公開：1リポジトリに5,000エージェント・毎秒7,200 push を社内試験、限定プライベートプレビュー

DEVPM

GitHub ブログ（11月5日）は、エージェントの増加で混雑するリポジトリに対応するための新しい Git ストレージ構成を説明した。ある1リポジトリの1日あたりのリクエストが3月から5月で約4倍になったという。Git オブジェクトは内容で名付けられた不変データなので調整なしに保存でき、合意が必要なのは参照の更新だけという考えから、データは Azure Blob Storage に置き、参照とパック管理は複製ログ（Ref-CAS）で扱う。社内試験では5,000の同時エージェント、毎秒7,200 push、参照操作は毎秒数万件を達成した。利用者の操作や保護機能は従来どおりで、限定プライベートプレビュー、広い提供は来年初めの予定。

  • DEV今すぐ使える機能ではないが、エージェントが1リポジトリに大量に push する運用で起きるボトルネックの種類（参照更新の競合）を知っておける。
  • PM並列エージェントを増やす計画では、リポジトリ基盤側の上限も検討項目になる。提供は来年初めの見込みで、それまでの運用上限は現行のままである。
