Anthropic は11月9日、Fable 5.2 と Mythos 5.2 を発表した。両者は同じ基盤モデルで、Fable はサイバー・生物分野の安全策を強めて全ユーザーに提供し、Mythos は検証プログラムを通った組織に限る。出力は 5.1 比で最大30%速く、任意の fast モード（最大2.5倍速、価格は2倍）も Claude Code などで使える。Claude アプリと Claude Code の既定は medium effort で、5.1 より少ないトークンで作業を終えるとする。社内比較では FrontierSWE v2 で 69.9%（Opus 5.5 は 62.3%）など上回るが、Anthropic 自身は「ほとんどのコーディングと知識作業の日常用途は Opus 5.5、最も難しい作業に Fable」と位置づけた。安全分類器に止められた要求は旧モデルへ落ちる仕組みで、ブロックは 5.1 比約55%減。API の ID は claude-fable-5-2。

  • DEV難所だけ Fable に回し、通常は Opus 5.5 という使い分けがベンダー公式の推奨になった。セキュリティ系タスクは分類器で別モデルに落ちる場合がある点に注意。

Amazon 社内のチケット分類で Claude Sonnet 4.6 を決定モデル「Strands Decider」に置き換え——1件あたり費用は約98%減、応答は78%短縮。旧新を本番で並走させて差分を見てから切り替え

Strands Agents チームのブログ（11月9日）によると、Amazon の大規模な社内チケットシステムで約20カテゴリへのラベル付けを担っていた Sonnet 4.6 を、テキストを生成せず選択肢ごとの確率と確信度だけを返す Strands Decider（Gemma 4 E4B ベース）に置き換えた。長いプロンプトは「各ラベルの1〜2文の基準＋該当なし」という単一の選択問題に書き直した。平均応答は 4,215ms→897ms、1件あたりトークンは 6,724→2,010（出力は170→1）、費用は約$0.0222→約$0.0005。検証は AppConfig の3段スイッチ（旧のみ／並走／新のみ）で本番トラフィックに両方を流し、不一致を確認した。ロールバックは約45秒。精度は「同等」とするが具体的な数値は示していない。

  • DEV「閉じた選択肢・高頻度・低遅延」の判断を大モデルから外す設計の実例。JSON のキー順で確率が最大0.19動いたので、リクエストのキーをソートするという細かい知見もそのまま使える。
  • PM旧新並走→差分レビュー→切替の段取りと、45秒で戻せるスイッチは、AI 機能の移行計画のひな形になる。
  • CONSULT問い合わせ分類・振り分けを生成 AI で回している顧客には、費用を桁で下げる選択肢として示せる。
どう試す／どう対応する：自社・顧客の LLM 呼び出しのうち「出力が数語のラベルだけ」の処理を洗い出し、件数と単価を一覧にする。候補を1つ選び、まず並走モードで1週間分の不一致率を測る。

Hugging Face Transformers に「decision」パイプラインが追加——テキストを生成せず、選択・スコア・真偽の確率だけを返すモデルを標準の書き方で呼べるように

DEVPM

Hugging Face は11月10日、決定モデル（decision models）への対応を発表した。状態（入力文脈）と質問の組を渡すと、生成ではなく、あらかじめ決めた答えへの確率分布を返す。質問の型は choice（選択）、score（順序尺度の期待値）、noul（真偽の確率）の3種。Transformers に pipeline("decision", ...) と AutoModelForDecision が加わり、Hub には decision-model タグ、transformers serve と llama.cpp には /v1/systemone エンドポイントが用意された。例として GEV-26B-Decide、JEV-9B、Kev-4B-GGUF などを挙げ、概念の起源を TypeSafe AI の Jev としている。ファインチューニング例も載るが、TRL の正式対応は未マージで、ベンチマークは示していない。

  • DEV決定モデルがベンダー固有 API でなく、Transformers・llama.cpp の標準機能で手元実行できるようになった。ローカルで判断部分だけを試す障壁が下がった。
  • PM上の Amazon 事例と合わせ、「判断は小さなモデル、生成は大きなモデル」という分担が技術選定の選択肢として定着しつつある。

KPMG ジャパンは11月10日、生成 AI・AI エージェントの全社展開に伴う費用を管理する支援サービスを発表した。エージェントの多段推論や再試行、外部ツール呼び出しで増える直接コストに、導入・運用・統制のコスト、業務変革や人材育成の間接コストを加えた3層で総コストを可視化する。「AI 資産の把握」「契約・課金モデル」「需要予測」「コスト監視」「統制・最適化」の5視点で診断から定着まで支援し、利用上限や部門配賦に加えて、モデルルーティング、プロンプトキャッシュ、コンテキスト・メモリ設計を設計段階で組み込む「Cost by Design」を掲げる。ユースケースごとに成果指標と Cost per Outcome を定義し、CDO・CIO・CFO が採算を継続評価できるようにするという。

  • CONSULTBig4 が AI 費用統制を独立メニュー化した。顧客から同種の相談が来る前提で、自社の提案にもモデル使い分け・キャッシュ・成果単価の枠組みを用意しておきたい。
  • PM「成果当たりのコスト」をユースケースごとに先に定義する、という考え方は自プロジェクトの KPI 設計にもそのまま使える。

何週間も動く長期エージェントには「耐久実行（durable execution）」が要る——ただし「耐久」は「正しい」ではない。martinfowler.com が設計パターンを整理

DEVPM

Thoughtworks の Kiran Prakash は11月10日、人や外部システムを待ちながら数週間続くエージェントには、外部に触れる各ステップの結果を記録し、障害後は記録を再生して状態を戻す耐久実行が必要だと論じた。Temporal、Cloudflare Workflows、Restate、Inngest、DBOS などを挙げ、べき等キーを再試行でも変えない、取り消せない操作は補償処理（saga）で戻す、承認や見積に期限を付けて実行前に事実を再確認する、といったパターンを示す。要点は「ランタイムが直すのは一般的な分散システムの障害だけ」で、古い情報や検証されていない外部テキストに基づく行動は、ツール内の決定的なチェックやコードでのルール強制でハーネス側が防ぐ必要があるという点。生成に Claude、次のツール選択に決定モデル Jev を使う構成例も載る。

  • DEV長時間エージェントを作るなら、プロンプトより先に「どのステップを記録し、どれをべき等にするか」を設計する。ルールはプロンプトでなくツール側に置く。
  • PM業務ルール変更時に実行中のワークフローをどう扱うか（旧ルールで完走させる並行変更）を、リリース計画の確認項目に加えられる。
出典：martinfowler.com「Long-horizon agents and durable execution」（2026-11-10）
コメント：エージェントの信頼性を「モデルの賢さ」から「分散システムの古典」に引き戻してくれる良い整理。

claude.dev ブログ（11月9日）は、リーダー1体と補助999体の Fable 5.2 チームでフェルマーの最終定理の Lean 形式化を約28.7時間で完了した実験を報告した。調整は共有 Postgres（指示・割当・メモ・サブタスク・完了記録の5表）と Git のみで、メッセージ機能は持たせない。各エージェントは専用の軽量 VM で、ネットワークなし・認証情報なし・sudo なし、外部への出口は身元を付与するゲートウェイ1本。自分のブランチにだけ push でき、統合は別ジョブが判定する。各ツール呼び出しは実行前に LLM 分類器が検査し（失敗時は遮断）、事後にも監視する。100万回超の呼び出しで遮断に至ったものはなかった。出力トークンは9月の同種実験の約3分の1。著者自身が「おもちゃの実験」と位置づけている。

  • DEV多数のエージェントを並列で動かすときの隔離・最小権限・ブランチ単位の統合という構成は、社内のエージェント基盤設計のチェックリストとして使える。
  • PM「補助エージェントが早々に不可能と判断した課題の多くが実は解けた」という観察は、エージェントの見積・諦め判断を人が見直す工程が要ることを示す。
