Claude Code の「作業ディレクトリ外への書き込み禁止」設定は Bash・PowerShell に効かない——Windows での実測と、PreToolUse hook による止め方

DEVPMCONSULT

Zenn の実測記事（11月2日）によると、Claude Code 2.1.314 で入った permissions.blockWritesOutsideWorkingDirectories を true にしても、対象は Write・Edit・NotebookEdit だけだった。Windows 11（Git for Windows、PowerShell 5.1）の Claude Code 2.1.316 では、Bash の echo >・cp や PowerShell の Set-Content で作業フォルダの外にファイルが作られた。bypassPermissions でも通常モードでも同じ結果である。Write は絶対パス、..、8.3 短い名前、ジャンクションなど7通りの書き方をすべて拒否した。一方、フォルダ内のパスを全大文字や短い名前で書くと誤って拒否される例もあった。旧版の 2.1.303 ではこの設定が警告なしに無視された。記事は、Bash|PowerShell に PreToolUse hook を掛け、コマンド中の外向きパスを終了コード 2 で止める方法を示す。ただし cd 後の相対パスや変数、rm -rf ~ は止められず、ネイティブ Windows では sandbox が効かない（公式文書の記述）ため、確実に防ぐなら WSL2 を勧めている。各ケース1回の実測である。

どう試す：Windows で Claude Code を使うメンバーは claude --version が 2.1.314 以上か確認し、設定を入れたうえで、捨てても良いフォルダで Bash から外への echo > ../x.txt を試して実際に止まるか確かめる。止まらなければ記事の PreToolUse hook を導入する。
  • DEV「設定を入れたから安全」と思わず、Bash 経由の書き込みは別の手段（hook、WSL2、sandbox）で塞ぐ必要がある。
  • PMエージェントの権限統制を「設定済み」で報告させるだけでは不十分で、実際に止まるかの動作確認を受け入れ基準に入れられる。
  • CONSULTクライアントの Windows 端末でエージェントを展開する案件では、権限設定の効く範囲と OS 差を説明し、WSL2 を含む構成を提案できる。
出典： Zenn「Claude Code の作業ディレクトリ外の書き込み禁止は Bash・PowerShell に効かない：Windows の実測と止め方」（2026-11-02）

Zenn「コードレビューより設計レビュー」——AI が書く前に計画を人が確認し、コードレビューでは「頼んでいない変更が足されていないか」の1点を見る

DEVPM

Zenn の記事（11月2日）は、AI が書いた PR を人がどこまで読むべきかという問いに、人のレビューの重心をコードから設計に移す答えを出す。手順は、AI が実装前に計画を書き、人が「要件と合っているか」「どこを触るか」「データや API の形」の3点を確認し、通った計画を実装用の指示書にする。実装を担当する AI には設計判断をさせず、指示書どおりに書かせる。指示書への適合は AI のレビューで確かめ、軽いレビューは実装のたびに、重いレビューは PR 作成前に観点別に並列で回す。最後に人がコードレビューで見るのは「要件にないものが AI の判断で足されていないか」の1点で、設計で触る範囲を先に決めているため範囲外の変更が見つけやすくなる。著者は、設計の範囲外で起きたことは設計レビューでは防げないため、コードを全く読まないわけではないと断っている。

  • DEV計画の確認項目が3点に絞られており、既存のレビュー手順にそのまま足せる。
  • PMレビュー工数を、実装後の差分読みから、短い計画の確認へ前倒しする案として、チームの運用ルールの議論に使える。
