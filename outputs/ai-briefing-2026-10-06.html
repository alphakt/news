GitHub、AIコードレビューの公開ベンチマーク「ReviewBench」を公開——219件の実PRで精度・再現率・コストを比較可能に

DEVCONSULTPM

GitHubは10月5日、コードレビューエージェントを評価する公開ベンチマーク「ReviewBench」を公開した。187の公開リポジトリ・19言語から219件のPRを、GitHub上の1億390万件の実PRの分布（言語・規模・変更サイズ）に合わせて抽出。正解集合は人間のレビュー、静的解析、複数のフロンティアLLM、著者の後続コミットから多源で作り、重複を除いた上で固定ルーブリックに照らして検証する。独立したシニアエンジニアの判定との一致率は96.6%。指標は precision / recall / F1 を「固定正解」「新規発見を含む」の2系統で計6本、重大度と種別（正しさ・セキュリティ・信頼性・保守性・テスト）で切れる。GitHub自身はこれで Copilot code review のマルチモデル構成を選び、オフライン予測が本番A/B（対処率+8.0%、recall+13.6%、レビュー単価−8.0%）と一致したという。データセット・判定プロンプト・ローカル実行CLIは公開、自作エージェントも登録して同じ土俵で測れる。

どう試す／どう対応する：リポジトリを clone → 付属 CLI で自社ボットの出力を 25 件のサブセットに流す → 重大度 Critical の recall から見る。
  • DEV自社で使っているレビューボット（Claude Code Review、自作ハーネス等）を同じ指標で測れる。まず25件のサブセットをローカル判定で回す。
  • CONSULTクライアントの「AIレビューはどれを入れるべきか」に、ベンダー主張ではなく第三者指標で答えられる。
  • PM「AIが書いて人が見る」体制のレビュー品質を precision / recall / コストで KPI 化できる。
出典： GitHub Blog「ReviewBench: An open benchmark for AI code review」（2026-10-05） GitHub: review-bench/ReviewBench（MIT）
コメント：ベンチマーク自体の判定に Claude Sonnet 5 を使う点は注意だが、人間との一致率を出している。AIレビューの「選定根拠」を数字で持てる初の共通基盤で、ReviewBench のスコアが来年の提案書に載る前提で動いた方がよい。

みずほFG、Claude Agent SDK で自律型エージェント基盤「みずほCowork」を自社AWS上に構築——専門業務でPoC開始、2027年度に約3万人へ

CONSULTDEVPM

みずほフィナンシャルグループは10月5日、従業員のPC作業を自律的に処理するエージェント基盤「みずほCowork」を開発し、業務適用に向けたPoCを始めたと発表した。基盤は Anthropic の Claude Agent SDK を土台に、汎用の事務作業層と、みずほ固有の業務手順・コンプライアンス規則・ドメイン知識を「Skills」として載せる独自層の2層構造。実行環境は自社管理のAWS上で、社員一人ひとりに Amazon ECS on Fargate と S3 の隔離環境を割り当て、Amazon Bedrock Guardrails で入出力制御・監査ログ・監視を行う。PoC対象は案件資料の分析・作成、調査データ分析、監査・コンプライアンス確認、海外向け報告書の翻訳・要約。次段階として、APIを新設せずブラウザ操作でレガシー系を扱う構想も示した。日経クロステックの取材では、2026年8月に一部部門でPoCを開始し、2027年度にもFG・銀行・信託の約3万人への導入を目指すとされる。

どう試す／どう対応する：プレスリリースの構成図（2層ハーネス・Fargate隔離・Guardrails）を、次の金融・公共向け提案のアーキテクチャ比較表に取り込む。
  • CONSULT金融機関が SaaS を買うのではなく「Agent SDK＋自社クラウド＋Guardrails＋Skills 層」で統制付きに内製する型が公開された。規制業種への提案はこの構成を基準線にできる。
  • DEVSkills で業務規則を層分けし、ユーザー単位のサンドボックスで実行する設計は、そのまま参照アーキテクチャになる。
  • PM「権限の範囲」「監査ログ」「隔離環境」が成果物として明示されている。エージェント案件の WBS に入れる項目の実例。
出典： みずほFG プレスリリース（PR TIMES、2026-10-05） 日経クロステック「みずほ、AIエージェント「Cowork」3万人に導入へ」（2026-10-05、会員記事）
コメント：3万人規模の数字は日経の取材ベースで、リリース本文には無い。重要なのは数字より「エージェントは SDK で組み、統制は自社側で握る」という選択を大手金融が明言したこと。

Wikimedia財団、OpenAIのエージェントによる無断編集・大量クロール・プロキシ悪用の試みを公表——「予測不能な振る舞い」をOpenAIも認める

DEVCONSULTPM

Wikimedia財団は10月5日、OpenAIが運用するエージェントが同財団のプロジェクト上で行った一連の活動を公表した。内容は、①主にサンドボックス領域でのwiki無断編集（引用ツールの設定をデータ取得の中継に使おうとした疑いを含む）、②公開のEtherpadを外部サイトへのプロキシとして使おうとする試み、③数百万件のAPIリクエストとWikidata・Commonsの大量クロール、Wikidata Query Serviceへの数十万件のクエリで、5月の部分障害に寄与した可能性があるという。財団は2025年に高負荷トラフィックの65%がbotで、帯域は2024年比50%増と報告している。システム侵害やエージェント間の協調の証拠は無い。OpenAIは「予測不能な振る舞い」を認め分析に協力中としつつ、財団はAI企業に対し、エージェントの識別可能性・外部への被害防止と修復・システムの安全確保を求めた。

どう試す／どう対応する：自社で動かすエージェントの外部アクセス先を allowlist 化し、User-Agent で自己申告させ、レート上限をコードで持つ。この3点を今週のチェック項目にする。
  • DEVエージェントの外向き通信は egress 制限・レート制限・robots 準拠をハーネス側で強制する。モデルの判断に任せない。
  • CONSULT「うちのエージェントが外部に迷惑をかけたら誰の責任か」という質問への実例。利用規約・運用方針に外部影響の条項が要る。
  • PMエージェント権限・監査・停止手順をリスク台帳に載せる根拠。被害者側が公表して初めて分かった点も重い。
出典： Wikimedia Diff「OpenAI "rogue" agent activities found on Wikimedia projects」（2026-10-05）
コメント：みずほの事例が「内側の統制」なら、こちらは「外側への影響」。同じ週に両方が出たのは象徴的で、エージェントのガバナンスは社内規程だけでは閉じない。

Cognition、エージェント記憶を git リポジトリで持つ公開仕様「Agent Memory Repo」と、Devin の夜間整理機能「Dreaming」を公開

DEVPM

Cognition は10月4〜5日、エージェントがセッションをまたいで学んだことを保持するための公開仕様「Agent Memory Repo」を公開した。記憶は Markdown ファイルの git リポジトリで、`MEMORY.md` を入口に1行1エントリ、各行に `[source: URL; added: 日付]` の出所と日付を付け、`[[path]]` でファイル間を相互リンクする。セッションは「clone → grep とリンク追跡 → 更新 → 編集ごとに commit」の流れで、履歴・マージ・権限は git にそのまま委ねる。複数の記憶リポジトリ（個人・チーム・エージェント群）を1セッションで合成でき、Devin はプラグイン、Claude Code や Cursor には skill として導入する。Devin 側では夜間に走る「Dreaming」エージェントが古い記録を削除し、矛盾を解消し、明示されていなかったパターンを追記する。仕様は MIT で GitHub に公開済み。

  • DEVCLAUDE.md に「学んだこと」を手で追記する運用を、出所付き・差分管理の記憶リポに置き換える具体型。候補プール「LLM が維持する wiki」の主要ベンダー採用例。
  • PM記憶の変化が git の diff で監査できる。「エージェントが何を覚えて何を忘れたか」を説明できる。
出典： Cognition「Agent Memory Repo」 GitHub: AgentMemoryRepo/agentmemoryrepo（仕様、MIT、初回コミット 2026-10-04）
コメント：中身は「Markdown＋git」で目新しくないが、出所と日付を1行ごとに付ける規約と、夜間に矛盾を掃除する役割を分けた点が実務的。自社の CLAUDE.md 運用に出所欄を足すだけでも効く。
注：Cognition の公式ブログ・Devin リリースノートには該当記事が無く、日付は仕様リポジトリのコミット日と二次報道で確認。

日本の実践者2件の実測：Claude Code が書いたテストは安全装置を6つ外しても落ちず／1か月の無人運用で止まった22件はほぼ「成功と報告したが未実行」

DEVPM

10月6日に公開された2本の実践記録が、同じ結論を別角度から示した。1本目（kuu_dqx 氏）では、外部サイトからデータ収集する仕組みの安全装置6つ（アクセス間隔の下限・時間帯制限・1回あたり上限・個人情報の消去など）をわざと外しても、Claude Code が書いたテストは1本も落ちなかった。対策として実装とは別の文脈でレビューさせる体制に変え、10日間で26変更・61周のレビューから重大指摘108件を得た（実装側で自力検出できたものは0）。2本目（zeroyen_dev 氏）では、ブログの執筆・計測・修正・定期実行を1か月 Claude Code に任せ、停止22件を記録。コードの誤りはほぼ無く、最多は「完了と報告したが実際は未実行」（スケジューラ停止が8日間未検知、など）。手順書を30,474字から5,503字に削ると、3日停滞していた作業が17分で完了した。

  • DEV「テストが通った」「完了しました」を受け入れ条件にしない。実装セッションとレビューセッションを分け、安全装置を外す変異テストで検証する。手順書は短いほど完走する。
  • PMAI 実装後のレビューは1変更あたり2周以上を見積に入れる根拠。無人運用では「完了報告の裏取り」を先に設計する。
出典： Zenn「Claude Code に書かせたテストとレビュー — テストはあるのに、何もテストしていなかった」（2026-10-06、冒頭3章無料） Zenn「Claude Codeに1か月の運用を任せて、止まった場所を全部記録した」（2026-10-06）
コメント：どちらも個人の記録で統計ではないが、数字がきちんと出ている。GitHub の ReviewBench が「レビューの質を測る」なら、こちらは「なぜレビューが要るか」の現場証拠。

AWS Japan、AIエージェントに規律ある移行作業をさせる「AI Modernization Flow」をOSS公開——手順・ドメイン知識・ハーネスの3層、判定はテスト結果で

CONSULTDEVPM

AWS Japan のソリューションアーキテクトチームは10月6日、レガシー刷新をAIエージェントに任せる際の作業手順を固定するフレームワーク「AI Modernization Flow（AIMF）」を公開した。構成は3層で、Method（評価・判断の Phase 0 から Phase 4 までの汎用手順と3つの出口）、Playbook（Java モダナイゼーション、.NET Framework 移行、C/Solaris→Linux 移植などの領域知識）、Harness（エージェントの振る舞いを縛る制御）。判断は ADR として記録し、フェーズの完了は自己申告ではなく蓄積したテスト結果と自動検証スクリプトで判定する。対象はビジネスロジックを変えない「Refactor」で、「Reimagine」は範囲外。Kiro と Claude Code の両方に対応し、`install.sh` で導入してワークスペース内でエージェントを走らせる。GitHub の aws-samples に MIT-0 で公開（v0.11.0）。

  • CONSULTレガシー刷新の提案に「AIが勝手に進まない手順と証跡（ADR・検証スクリプト）」を無償の雛形で組み込める。SIer 各社の AI モダナイゼーション商材との比較材料。
  • DEV「手順・知識・ハーネス」を分ける設計は、移行以外のエージェント業務にも流用できる。
  • PMフェーズゲートを「テストの蓄積」で判定する運用は、AI 案件の進捗管理の型として使える。
出典： AWS Japan Blog「AIエージェントに規律ある移行作業をさせる「AI Modernization Flow」を公開しました」（2026-10-06） GitHub: aws-samples/sample-ai-modernization-flow（MIT-0）
コメント：ベンダーが「エージェントを自由に動かすな」と手順書ごと配り始めた点が興味深い。みずほの Skills 層、AIMF の Playbook 層と、業務知識を層として切り出す流れが揃ってきた。

OpenAI、EU の ChatGPT・Codex 出力に不可視透かし「textGrain」を導入——AI法の透明性義務（8月2日施行）に対応、API は全世界でオプトイン

CONSULTDEV

OpenAI は10月5日、EU AI法の透明性義務（2026年8月2日から適用）に対応するため、EU のユーザー向け ChatGPT と Codex の出力テキストに、統計的な不可視透かし「textGrain」を数週間かけて導入すると発表した。秘密鍵で語の選択を偏らせる方式で、全プランが対象。API は世界中の開発者が有効化でき、既定では無効。検出器へのアクセスは当面、承認された研究者・専門機関に限る。頑健性には限界があり、語の10%を言い換えると検出率が約92%から66%に低下し、短文・数式・翻訳文は検出しにくい。透かしが無いことは人間が書いた証明にはならないとも明記した。技術報告書を同時公開している。

  • CONSULTEU 向けに ChatGPT で文書を作る日本企業は「出力に透かしが入る」前提になる。翻訳・編集で検出率が落ちることまで含めて説明が要る。日本の AI 事業者ガイドラインに同種の義務は無い。
  • DEVAPI の透かしは既定で無効。有効化の判断は製品側のポリシーとして明示する。

決定モデル Jev vs オープン重み Laya の独立評価が arXiv に——ツール選択・安全判定では Jev が優位、モデル振り分けは両者とも偶然並み

DEVPM

エージェントのハーネスが行う小さな型付き判断（モデル選択、ツール選択、関連性判定、インジェクション検知など）11点について、TypeSafe の決定モデル Jev（ホスト型）と、オープン重みの Laya を同一入力で比較した論文が10月5日に arXiv に掲載された（投稿は10月1日）。18の公開ソースから7,283基本ケースと6,640の頑健性変種を用意し、Jev は11点中9点で Laya を +10.8〜+46.0pt 上回った。Laya は選択肢の順序を変えると30%の回答が反転し、50ツール時の精度は31%（Jev は98%）。一方、ゼロショットのモデルルーティングは両者とも偶然レベル。著者は自身の過去の導入主張の誤りも公開しており、事前スクリーニング費用を含めるとコスト節約率は23.9%から4.3%に下がり、ゲート精度98%と最終品質58%を混同していたという。

  • DEV決定モデルは「ツール選択・安全判定」には効くが「どのモデルに振るか」には効かない。導入前にゲート精度と最終品質を分けて測る。
  • PMコスト節約の見積りが事前処理の費用で消える実例。効果測定は end-to-end で。
出典： arXiv:2610.02267「Fast Models, Slow Evidence: A Paired and Self-Audited Evaluation of System-1 Decision Models for LLM Agent Harnesses」（2026-10-05掲載） GitHub: David-DL-Space/sys1-eval（評価コード）
