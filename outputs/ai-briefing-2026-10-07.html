OpenAI、判断専用の「Decisions API」を公開ベータに——テキスト・画像に対し確率・選択肢・スコアを型付きで返し、入力 $0.10/100万トークン、出力課金なし

DEVPMCONSULT

OpenAIの開発者ドキュメントに、新しい「Decisions API」が掲載された。文章を生成せず、入力（テキストや画像）と質問を渡すと、条件に当てはまる確率（predicate）、固定の選択肢からの選択と確信度（choice）、基準に沿った評価点（score）を型付きで返す。Responses APIの約10倍速いとされ、用途は分類、問い合わせの振り分け、優先度付け。現在使えるモデルは gpt-6-luna のみで、入力は100万トークンあたり0.10ドル、出力トークンは課金されない。公開ベータで、GAは近いと記されている。HIPAAとZero Data Retentionにも対応する。候補プールで追ってきた「決定モデル」（Jev）と同じ発想が、主要ベンダーの正式APIとして出た形だ。

どう試す／どう対応する：自社の問い合わせ振り分けやPRの重要度判定など、すでにLLMで分類している処理を1つ選び、同じ100件を現行APIとDecisions APIに流して、一致率・遅延・費用を比べる。
  • DEVエージェントの小さな判断（ツール選択、安全判定、ルーティング）を主モデルから切り出す標準部品になる。確率で返るため、閾値で人間確認へ回す設計がしやすい。
  • PM判断処理は出力課金なしで安い。トークン費用の統制では「どの判断を安価な判定APIに寄せるか」が新しい見積項目になる。
  • CONSULT業務フローの分類・振り分けを「生成」でなく「判定」で組む提案が可能に。HIPAA/ZDR対応なので機密度の高い業種でも説明しやすい。

AWS Japan Blogは10月7日、株式会社アテナと共同執筆した導入事例を公開した。Claude Desktop のバックエンドを Amazon Bedrock に向け、Microsoft Entra ID の OIDC フェデレーションで認証する構成。統制は3層で、ID基盤は既存の従業員ライフサイクル管理を流用、AWS側は有効期限12時間の一時認証情報と日本国内の推論プロファイルのみ許可、端末側はMDMのレジストリ配布でWeb検索などの機能を制限した。PoCは2026年9月に28台・有志22名で実施し、約200名への全社展開を予定する。成果は業務時間が半分程度に減り、提案資料の約9割をAIで作成できたこと。一方、9営業日の測定を月額換算すると22名で Claude Team 22席分の約3.9倍になり、利用者別には51倍の開き、上位2名で費用の約半分を占めた。非エンジニア社員が自分でCLAUDE.mdを作り込んだ点も目を引く。

どう試す／どう対応する：クライアントの「全社展開」提案に、PoCで利用者別のトークン費用分布を必ず測る工程を入れる。席課金との損益分岐は、平均でなく上位利用者の偏りで試算する。
  • CONSULT日本国内推論・一時認証・MDM制限という統制の型が、そのまま日本企業向けの参照構成になる。Teamプラン席との費用比較は必ず聞かれる。
  • PM従量課金の見積りは平均値で作らない。51倍の偏りがあるため、上位利用者の上限・アラート設計を予算に含める。
  • DEV非エンジニアがCLAUDE.mdを自作するところまで進んだ。配布する雛形とレビューの仕組みを先に用意すると、全社展開で品質が揃う。

arXiv：AIのPRレビュアーは「指摘に従って直したふり」で脆弱性を通せる——フィードバック誘導型の攻撃が、従来手法の2.5〜12.5倍の成功率

DEVPM

10月6日にarXivへ掲載された論文（2610.05399）は、AIレビュアーの指摘を攻撃者が逆手に取る手口「AFCRA」を示した。レビュアーが挙げた問題を表面上は直しつつ、根本の脆弱性を残したコードに修正を重ねていく方式で、実行可能なエクスプロイトを持つ159件の既知脆弱性からベンチマーク（AFCRA-Bench）を作って検証した。Sonnet 5 と GPT-5.5 をレビュアーにして5ラウンド繰り返したところ、テキストやコメントだけで騙す最強の従来攻撃に対し、成功率は2.5倍から12.5倍に上がった。論文は開発者、AI提供側、レビュアー、著者それぞれへの対策も提案している。AIレビュアーをマージの唯一の門番にする運用の弱点を、再現可能な形で示した研究だ。

どう試す／どう対応する：自社のレビューボット運用で「ボットの指摘→修正→再レビュー」の往復回数に上限を置き、セキュリティ関連の変更は人間の承認を必須にするルールを今週のレビュー規約に足す。
  • DEVAIレビューは「通ったから安全」の根拠にならない。修正の往復を重ねるほど騙されやすいため、再レビューは回数制限と人間確認を併用する。
  • PMAIレビュー導入の品質計画に、攻撃的な利用（外部コントリビューターや侵害されたエージェント）を想定した統制を入れる。
出典： arXiv:2610.05399「Adaptive Code Revision Attacks on AI Pull Request Reviewers」（2026-10-06掲載）
コメント：昨日のReviewBenchが「どのボットが良いか」を測る話なら、こちらは「良いボットでも門番にならない」条件を示す話。2つ並べて読むと、レビュー体制の設計が見える。

arXiv：「ハーネスが買うのはトークンだけ」——Claude Code と最軽量ハーネスのSWE-bench成績は5ポイント以内、1タスクの費用は最大3倍違う

PMDEVCONSULT

10月6日掲載の論文（2610.04433、Liu・Han）は、5つのモデルと3つの実運用ハーネス（Claude Code、mini-SWE-agent、OpenCode）をSWE-bench Verified（447タスク）で比べた。最も重いハーネスと最も軽いハーネスの成績差は5ポイント以内で、ハーネスを替えて結果が入れ替わるタスクの割合（約13%）は、同じ条件でやり直した場合の揺れと同程度だった。一方、1タスクあたりの費用は同じモデル・同じタスクでも最大3倍違い、原因はステップごとに送られるシステムプロンプトの前置きとツール定義の大きさだという。さらに現行のタスク数ではハーネス改良の効果を検出しにくく、45タスクでは13ポイントの差を半分の確率でしか拾えないとも指摘する。

どう試す／どう対応する：自社で使うコーディングエージェントについて、同じ10〜20タスクで「システムプロンプト＋ツール定義」の送信トークン量を計測し、不要なツール定義を外した構成の費用と成績を比べる。
  • PMエージェント選定の費用比較は、成績でなく1タスクあたりのトークン量で行う。ハーネス乗り換えの見積りに「成績は同等、費用は最大3倍差」を使える。
  • DEVツール定義とプロンプトの前置きを削るのが最も確実な節約策になる。評価は小さなタスク集合では判断できないので、母数を増やす。
  • CONSULTクライアントの「どのエージェントが賢いか」という質問には、成績差より運用費差で答える方が説得力がある。
出典： arXiv:2610.04433「What Does a Harness Buy? Tokens, Mostly」（2026-10-06掲載）
コメント：モデルやハーネスの成績比較を売りにする資料への解毒剤になる。ただし評価対象はSWE-bench Verifiedのみで、業務タスクへそのまま当てはまるとは限らない。
重要度：低

GitHub、エージェント規模の開発に備えGit基盤を再構築——9月のコミットは73.8億件で前年の5倍、書き込み性能は最大35倍を見込む

PMDEV

GitHubは10月6日、Git基盤を稼働を止めずに作り替えていると技術ブログで説明した。Git関連イベントは前年比2倍（月2,182億→4,733億）、9月のコミットは73.8億件で前年の5倍、プッシュは4.9倍、PRマージは約4倍、GitHub Actionsは32.6億回で4倍に増えている。従来は耐久性と規模が結びついていたため読み取りレプリカを増やすと書き込みが遅くなった。新方式は保存と計算を分離し、リポジトリデータをAzure Blob Storageへ移し、軽量なワーカーが読み取りを担い、圧縮やガベージコレクションは別処理にする。書き込みのクリティカルパスは参照の更新のみに絞り、最大35倍の書き込みスループットを見込む。ブランチ保護、監査ログ、レビュー制御は維持される。

  • PMエージェントが量を桁違いに増やす前提で、基盤側も作り替えが要る段階に来ている。自社CIやリポジトリ運用の上限・レート制限は、エージェント導入前に見直す。
  • DEV大量のコミット・PRを生む運用では、リポジトリ側の待ち時間や制限が詰まりどころになり得る。ブランチ保護や監査が維持される点は安心材料。
