Microsoftが判断特化モデル「Microsoft-Decision-1」を公開——文章を生成せず選択肢ごとの確率だけを返し、入力100万トークン0.042ドル

DEVPMCONSULT

Microsoftは10月9日（米国時間）、Qwen3.5-9Bを追加学習した判断特化モデルをMicrosoft FoundryとOpenRouterで提供開始した。状況・質問・固定の選択肢（はい／いいえ、多肢選択、評価尺度）を渡すと、各選択肢の確率を1回の推論で返す。ルーブリックによるAI応答やエージェント行動の採点にも使える。価格は入力100万トークンあたり0.042ドルで、出力は無料。Microsoftは、学習に使っていない36のベンチマーク（約15万問）で最高精度、GPT-6 Solより中央値で約35倍高速としているが、いずれも自社測定である。Xbox研究部門は品質が同等で14倍高速・200倍安価と報告した。重大な判断の単独利用は避けるよう注意書きがある。判断特化モデルはTypeSafe AIのJev、OpenAIのDecisions APIに続く3例目で、「エージェントの小さな判断を主モデルから切り出す」設計が各社の標準部品になりつつある。

どう試す／どう対応する：自社エージェントの「ツール選択」「承認要否」「応答の合否採点」のうち1つを選び、OpenRouter経由でこのモデルに置き換えて、現行の主モデル判断と一致率・遅延・費用を比べる。
  • DEV分岐判断を確率付きJSONで受け取れるため、閾値で自動実行と人間確認を切り分けるゲートを短いコードで作れる。
  • PM判断呼び出しを小型モデルに分ければ、トークン費用と待ち時間の見積もりが変わる。ただしベンチマークは自社測定なので、自案件のデータで検証する工程が要る。
  • CONSULT「エージェントの判断をどう統制するか」という質問に、判断を分離して確率を記録する設計の具体例として示せる。人に関わる重大判断への単独利用は不可という条件も併せて伝える。
出典： Microsoft「Microsoft-Decision-1」（2026-10-09）
コメント：Jevに続く3社目で潮流は確定的だが、精度・速度の優位は各社が自社ベンチで主張している段階なので、乗り換えは自前評価を経てからにしたい。

Claude Codeのdenyに相対パス「../」を書いても隣のフォルダへの書き込みが止まらない——2.1.296での実測報告

DEVPMCONSULT

Zennの筆者が10月11日に公開した検証記事によると、Windows 10・Claude Code 2.1.296・非対話の claude -p で、.claude/settings.json の deny に Edit(../shared/partner/**) のような相対パスを書いても、Write・Edit・Bash（echo や node による書き込み）のいずれも止まらず、起動時の警告も出なかった。判定はダミーファイルのハッシュ比較による。同じ場所を絶対パスで書くと Write・Edit・Bash の echo は止まったが、Bash を自動許可していると node スクリプトからの書き込みは絶対パスでも止まらなかった。また deny の書き込み禁止は Write(...) ではなく Edit(...) で書く必要がある。筆者は、作業フォルダ外を守る規則は絶対パスで書く、Bash を自動許可しない、規則は書いたあと実際に止まるか試す、deny は壁ではなくブレーキなので OS の権限分離やコンテナも併用する、と述べている。検証は筆者1人の環境の結果である。

どう試す／どう対応する：自分の settings.json にある deny のうち「../」や相対パスで書いたものを洗い出し、捨てファイルを対象に Write・Edit・Bash で本当に拒否されるかを確かめる。止まらなければ絶対パスに書き直し、Bash の自動許可を見直す。
  • DEVdeny は書いただけでは効いている保証がなく、拒否されることを実際に試して確認する習慣が必要になる。
  • PMエージェントの権限統制を設定ファイルだけに頼る計画は危うい。環境の隔離（コンテナ・別ユーザー）を標準要件にするかを判断する材料になる。
  • CONSULT「エージェントに触らせない範囲を設定で守れるか」というクライアントの問いに、設定は補助でありOS・環境側の隔離が本体、と根拠付きで説明できる。
出典： Zenn「Claude Code の deny に ../ を書いたら、隣のフォルダへの書き込みが止まらなかった（2.1.296で実測）」（2026-10-11）
コメント：公式の仕様確認ではなく個人環境（Windows）での実測なので、Mac／Linuxや新しい版で同じかは別途確かめる必要があるが、確認コストが低いので先に自分の設定を点検する価値は高い。

Claude Codeのサブエージェント1体の消費を数え直したら、画面表示157,630トークンに対しログでは3,514,672トークン（約22倍）だった

PMDEV

Zennの筆者が10月12日に公開した記事で、調べもの担当のサブエージェントを1体走らせたところ、会話に表示された消費は157,630トークンだったが、Claude Codeが記録するログから数え直すと3,514,672トークンで、約22倍あったと報告している。測定は8月30日と9月21日に行われた。差の大部分はキャッシュ読み取りで、会話に出る数字には含まれていないという。筆者は、消費を減らすには文章量よりもやり取りの往復回数を減らす方が効く、定額プランでもサブエージェントを同時に複数走らせると使用量が跳ね上がると指摘する。なお原因分析の後半は有料部分のため確認できておらず、キャッシュ読み取りがどの料金区分でどう課金されるかは本文からは分からない。一人の実測であり、一般化には自分の環境での再計測が要る。

  • PM画面の表示値を基にしたトークン費用の見積もりは過小になりうる。コスト統制はログ集計を基準にする運用を検討する。
  • DEVサブエージェントの多用は往復回数を増やして消費を膨らませる。並列数と往復回数を設計時の指標にする。
出典： Zenn「Claude Code の担当が使ったトークンを数え直したら、画面に出た数字の22倍だった」（2026-10-12）
コメント：キャッシュ読み取りは単価が低いため、22倍がそのまま費用の22倍ではない点に注意しつつ、「表示値は全体像ではない」という前提だけは持っておきたい。
