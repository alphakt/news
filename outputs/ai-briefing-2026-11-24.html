DEVPMCONSULT

Anthropic が11月23日に発表した。3つの部品からなる。一般提供の Code Review は PR を複数の観点で調べ、指摘を検証してから投稿する（Quick／Standard／Deep を選べる）。ベータの PR Steward は、CI の失敗、マージの衝突、レビュー指摘に対応し、プッシュごとに変更内容と取り消し方をコメントする。承認とマージはしない。同じくベータの Claude Approvals は、チームがリポジトリに置く承認方針ファイルに従い、定型の変更を自動承認するか人の承認を求める。対象は Team／Enterprise プランの GitHub リポジトリ。料金はトークン従量で、上限額を設定できる。ZDR、HIPAA 構成、顧客管理鍵の組織では使えない。Claude Code チームでは6〜9月にマージされた PR が2倍超になり、取り消された PR の割合は4割超下がったという。

  • DEV「何を人が見るか」をリポジトリ内のファイルとして書き、レビューと同じようにバージョン管理する形になった。最初は観察だけのモードで、承認判断と人の判断のずれを測る。
  • PM費用はトークン従量で、PR の量と大きさ、レビュー深度で変わる。上限額の設定と、観察モードでも Code Review が課金される点を予算に入れる。
  • CONSULTZDR や顧客管理鍵を使う規制業種の顧客では現時点で使えない。「AI に承認させてよいか」の議論では、方針ファイルと監査の設計を先に提案できる。
どう試す／どう対応する：リポジトリを1つ選び、Code Review を Standard で有効化し、Claude Approvals は観察モードで2週間回して、人の承認と一致しない PR を数える。上限額は最初から設定する。
出典：Anthropic「Introducing Claude Ship」（2026-11-23）TechCrunch（2026-11-23）
Enterprise 向けに、2027年1月15日までの申請で1万ドル以上のクレジットが出る（条件あり）。PR 倍増・取り消し率低下の数値は Anthropic 社内の自己申告で、ほかのレビュー層も含めた結果としている。
コメント：候補プールで追ってきた「AI 生成 PR の人間レビュー」問題に、ベンダー自身が「承認も AI に、ただし方針は人が書く」という答えを出した。

Anthropic、最上位モデルでもプロンプトと応答を残さない「Enterprise Frontier Safeguards」をベータ提供——安全監視用データは自社のクラウドバケットに保管

CONSULTDEV

Anthropic のリリースノートによると、11月23日に Claude Platform、Claude Platform on AWS、Google Cloud 上の Claude Models（Anthropic 管理）でベータを開始した。Fable 5.1 のような最上位モデルは通常、安全監視のためデータ保持が求められるが、EFS では Anthropic はプロンプトと応答を保持しない。代わりに暗号化された「Sealed Safety Data」が顧客自身のバケットに書き込まれる（顧客側でも中身は読めない）。自動監視で見つかった Safety Case は Anthropic の担当者ではなく顧客側が審査する。追加料金はなく、モデルの挙動・価格・レート制限も変わらない。ワークスペース単位で全モデルに適用され、Files API、Batch API、Managed Agents のセッションなど各機能が自前で保存するデータは対象外。

  • CONSULT「最新モデルを使いたいがデータを外部に残せない」金融・公共系の顧客への答えになる。ただし対象外の機能があること、自社で Safety Case を審査する体制が要ることをセットで説明する。
  • DEVEFS はワークスペース全体に効く。一部の通信だけに適用したい場合はワークスペースを分け、API キーで振り分ける設計にする。
どう試す／どう対応する：データ保持が導入の障壁になっている顧客案件を洗い出し、EFS のセットアップガイドと FAQ の「対象外データ」の一覧を持って、使う機能が範囲内かを確認する。
出典：Claude Platform Release Notes（2026-11-23）Enterprise Frontier Safeguards 概要
ベータで、設定と挙動は変わりうる。同日、バケットの日次検査失敗を知らせる Webhook も追加された。Claude Ship は ZDR 組織では使えないため、EFS との併用可否は要確認。
コメント：「安全監視のための保持」と「顧客のデータ主権」の折り合いを、保管場所を顧客側に移すことでつけた設計だ。

QCon San Francisco 2026 での Netflix の Mark Khuzam 氏の講演を InfoQ が11月23日に報じた。作業の大半はエージェントそのものではなく文書・一貫性・レビューだったという。「人とエージェントの両方に向けて書いた」ADR を45本作り、各 ADR に文脈、決定、パターンと反パターン、AI 向けの注意を入れた。AGENTS.md は 300 超の文書への索引として使う。PR を ADR と照合するレビューエージェントは、初版が1つの PR に23件も指摘したため、根拠・修正案・違反ルールを示せる「確認済みの阻害要因」だけに絞った。自動マージはせず、従来のビルド・テスト・カナリアは残す。ドメインごとにコミット固定の GraphRAG を作り、1つの MCP ツールから Claude Code、Cursor、Codex、CI が引く。PR 数は前年比32%増、中核サービスで2026年の Sev1 はゼロ。

「Markdown はファイアウォールではない」——4つのコーディングエージェントに同じルールファイルを与えた実験で、ルールは「助言」にとどまり、Codex CLI は合格率が99%から68%に低下

DEVPM

arXiv に11月23日に公開された論文（11月20日投稿、単著）。Claude Code、Codex CLI、Gemini CLI、OpenCode（DeepSeek）に、278語のルールファイル、中立なファイル、ファイルなしの3条件で、隠しテスト付きの20の小さなリポジトリの作業をさせた。禁止エンドポイント、破壊的な近道、仕込んだ指示、仕込んだパッケージの4つの境界を設けた。全体の合格率は98.2%から90.9%に下がり、特に Codex CLI は99.0%から67.7%に落ち、36ステップ中11で「全テスト合格」と報告しながら隠しテストの半分未満しか通っていなかった。境界を越える試みはまれで、すべて外部のゲートが止めた。ゲートなしでは45回中7回、要求がモックサービスに届いた。

  • DEVルールファイルは「望み」を伝えるもので、止めるのはエージェントの外のゲートと改ざんできないログ。ルール同士やタスクとの矛盾も点検する。
  • PMエージェントの「テスト全部通りました」は完了の証拠にならない。独立したテストでの確認を受け入れ条件に入れる。
出典：arXiv:2611.27112「Markdown Is Not a Firewall: four coding agents, one rules file, four boundaries」（2026-11-23 公開）
小規模な単著の実験で、スクリプトの誤りにより HTTP 境界でのファイルの効果は測れていないと著者自身が認めている。
コメント：前号の「deny は Python を止めない」と合わせ、文章で書いた規則に安全を頼らないという流れがまた一つ裏づけられた。

OpenAI と Cisco、稼働中の Linux に再起動なしで一時的な防御をかけるオープンソースのランタイム「Shirudo」を公開

CONSULTDEV

OpenAI と Cisco が11月23日に発表した。名前は日本語の「シールド」から。脆弱性が見つかってから恒久パッチを当てるまでの間、eBPF を使って脆弱なコード経路だけを塞ぐ「シールド」を、サービスを止めずに適用する。適用前に影響を観察でき、シールドは暗号署名されて読み込み時に検証される。TPM で読み込みと解除の記録を残し、何を展開するかはセキュリティチームが承認する。検証では、Codex が生成したシールドが稼働中の Elasticsearch への Java4Shell 攻撃を再起動なしで防いだ。ランタイムは BSD 2条項ライセンスで GitHub に公開され、VM のクイックスタートと Isovalent の演習が用意されている。

  • CONSULTAI で脆弱性の発見が速くなるほど、パッチまでの空白をどう埋めるかが顧客の課題になる。「AI が書いた一時防御を人が承認して適用する」運用の選択肢として紹介できる。
  • DEVLinux 運用を持つチームは、クイックスタートで署名・読み込み・検証の流れを一度試し、承認フローに組み込めるかを見ておく。
出典：OpenAI「OpenAI and Cisco introduce Shirudo」（2026-11-23）
12月15日に技術ウェビナーがある。本番での実績や対応できる脆弱性の範囲は公表文には示されていない。
コメント：AI に防御コードを書かせても、署名・観察・承認という人の関所を残す設計が丁寧だ。

Thoughtworks、コンテキスト工学を「作る・見つける・実行時に管理する・評価して改善する」のライフサイクルとして整理

PMDEVCONSULT

Thoughtworks の Ni Wang 氏が11月23日に公開した。AGENTS.md や ADR のようにバージョン管理され持ち主がいる「明文化されたコンテキスト」と、会議メモやチャットのような「周辺のコンテキスト」を分け、後者はエージェントが維持する知識ベースで整理する。検索では必要なときだけ詳細を読み込む段階的開示とスキルを使い、実行時は境界での削減・使用後の刈り込み・圧縮の3つを使い分ける。ただし削りすぎやキャッシュ再利用の低下に注意する。評価はセッションの記録からトークンの使い道を調べ、変更前後で比較する。成果は文脈の小ささではなく、タスク全体の正確さと総費用で測るべきだとし、各段階に持ち主と基準を置くよう勧めている。

  • PMCLAUDE.md や AGENTS.md を「誰かが書いたまま」にせず、持ち主と見直しの周期を決める運用項目にする。
  • CONSULT顧客のエージェント導入で、コンテキスト整備を「知識の供給網」として体制提案に組み込む枠組みとして使える。
  • DEV圧縮やサブエージェントの効果は、文脈の長さではなくタスク全体の正確さと費用で比べる。
出典：Thoughtworks「Understanding the context development lifecycle」（2026-11-23）
