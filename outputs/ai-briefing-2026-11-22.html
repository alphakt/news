Kiro ブログが11月20日に発表し、AWS Japan が21日に翻訳を公開した。管理者が VPC を一度登録すると、以後のクラウドセッションはすべてその VPC に自動で接続され、社内の Artifactory や Nexus、パブリック IP のないステージングの DB、Direct Connect や VPN の先のオンプレミスにも届く。セッションはサブネット内の1台のホストとして扱われ、NAT・ファイアウォール・ネットワーク ACL が効き、VPC フローログにも残る。モデルや制御系への通信は Kiro 側にとどまり VPC を通らない。設定は5段階のウィザードで、セキュリティグループは管理者が1〜5個選ぶ。IAM Identity Center を使う Enterprise プランが対象。同時に「リモートワークスペース」も始まり、Kiro IDE から SSH でクラウドセッション、Dev Container、手持ちの VM や GPU マシンに接続できる。

  • DEV「クラウドのエージェントは社内の依存関係を取れないので結合テストは手元で」という分担が不要になる。devcontainer.json があればチームと同じ環境で動く。
  • CONSULT閉域網の顧客に、ネットワーク境界に穴を開けずにクラウド型エージェントを使う構成として示せる。外向き通信は顧客の DLP で制御できる点が説明しやすい。
  • PMエージェントの通信がフローログに残るため、監査部門への説明材料が既存の仕組みでそろう。
どう試す／どう対応する：Enterprise プランの検証環境で Kiro Settings > Manage VPC connections からステージング VPC を登録し、社内レジストリからの依存取得と結合テストをクラウドセッションに任せてみる。
出典：AWS ブログ「Kiro のクラウドセッションからプライベートネットワークにアクセスできるようになりました」（2026-11-21）「Kiro のリモートワークスペース」（2026-11-21）

AWS Japan、既存コードから AI エージェント向けの仕様書を起こす「Reverse Spec Flow」を公開——全記述にコードの行番号を付け、別の AI が照合、約15万ステップの Java CMS で誤りは約5%

CONSULTDEVPM

AWS Japan のソリューションアーキテクトが11月21日、AWS Samples で公開したワークフローを紹介した。仕様書がない、古い、ブラックボックスになったアプリのソースから、作り直し（Reimagine）の入力となる仕様書を作る。取り込み、コードグラフ、分析、仕様化（ISO/IEC/IEEE 29148準拠）、監査の5段階に分け、各記述に根拠のコード位置（path:line）を付けて、書き手と別の AI がソースと突き合わせる。確かめられないことは UNKNOWN として残し、完了は AI の報告ではなく点検スクリプト gates.sh の合格で判定する。仕様は現行技術の事実の層と、技術に依存しない業務ルールの層に分ける。Apache Roller（約15万ステップ）では約38時間で完了し、無作為200件の照合で約5%に部分的な誤り、完全な誤りは0件だった。

  • CONSULTレガシー刷新の提案で「まず仕様書を AI で起こす」工程に、手順・数字・限界（静的解析のみ、誤り約5%）つきの公開事例が使える。
  • DEV根拠の行番号、別 AI による検証、スクリプトによる完了判定、という3つの規律は、仕様化以外のエージェント作業にもそのまま移せる。
  • PM人の判断が要った場面が4種類に整理されており、見積もりで人の確認工数を置く場所の目安になる。
どう試す／どう対応する：github.com/aws-samples/sample-reverse-spec-flow を取得し、社内の小さめのレガシーアプリ1本で Phase 1（コードグラフ）までを流して、網羅の分母が実態に合うかを見る。
出典：AWS ブログ「[AI-Driven Modernization] 既存コードからAIエージェント向けの仕様書を起こす『Reverse Spec Flow』を公開しました」（2026-11-21）

OpenAI、推論の抜き取り対策を強化——GPT-6.2 Astra と Sol では推論が生成した会話に結び付き、前のメッセージを書き換えると以降の推論は破棄される

DEVCONSULT

OpenAI は11月20日、他社が自社モデルの推論を抜き取って学習に使う「敵対的蒸留」への対策をまとめた。モデル自体に抜き取りの試みを見分けて保護された推論を出さないよう学習させ、入力と出力の分類器で、ストリーミングを含む応答やツール呼び出しの引数への推論の漏れを検出して止める。API では、保護された推論をユーザー・ワークスペース・組織・モデル系列をまたいで再利用することを制限した。GPT-6.2 Astra と Sol では推論はそれを生んだ会話に結び付けられ、前のメッセージが書き換えられると、その後の推論は API が捨てる。古い系列のモデルはこれらの推論を読めない。違反の疑いがあるアカウント網には週に数千〜数万件の措置を取っているという。

  • DEV会話履歴を要約・圧縮して書き換えるハーネスでは、以降の推論が引き継がれず、性能やトークン消費が変わりうる。モデルをまたいで推論を渡す構成も見直しが要る。
  • CONSULTOpenAI の出力を使った自社モデルの学習を検討する顧客には、規約と検知の両面で締め付けが強まっていると伝えるべきだ。
出典：OpenAI「Combatting adversarial distillation」（2026-11-20）

Signal、OS に組み込まれる AI エージェントへの対抗策を発表——iOS 27 で画面撮影を遮断し「Siri AI をブロック」設定を追加、OS 各社にアプリ単位で AI のデータ取得を断る仕組みを要求

DEVCONSULT

Signal の Meredith Whittaker 氏が11月20日に公表した。Google の Gemini Intelligence や Apple の Siri AI の画面認識のように、OS に入った AI エージェントが画面を読み取って質問に答えたり操作したりすると、取り込まれたデータはローカルやサーバーに残り、Signal の暗号化では守れなくなる。対策として、iOS 27 ではアプリ内のスクリーンショットを遮断し「Block Siri AI」設定を加えた。Android では AI アシスタントが画面を読もうとするのを検知すると「画面セキュリティ」を自動で有効にする。macOS では遮断できないため、Siri の除外アプリへの登録を勧める。Apple・Google・Microsoft には、画面・ファイル・通知・API などあらゆる経路で AI のデータ取得をアプリが拒否できる、文書化された仕組みを求めた。Meta の Muse のような他社エージェントがアクセシビリティ権限を悪用する点も問題視している。

  • DEV機密を扱う業務アプリでは、OS の AI エージェントによる画面読み取りを脅威として設計に入れる必要が出てきた。各 OS のスクリーン保護 API の対応状況を確認しておきたい。
  • CONSULT金融・医療などの顧客の MDM 方針に「端末の AI アシスタントをどのアプリに許すか」という新しい論点が加わる。
出典：Signal Blog（Meredith Whittaker、2026-11-20）
スクリーンショットの遮断では、端末に保存済みのファイルの読み取りなど別の経路は防げないと Signal 自身が認めている。保護は設定で解除できる。
コメント：エージェントの権限設計はサーバー側だけの話ではなく、利用者の端末の上でも始まっている。

BTM、販売中のログ調査エージェント「TracisAI」の実行基盤を ECS から Amazon Bedrock AgentCore へ移行——顧客 VPC での導入のつまずきを減らし、従量課金にするため

CONSULTDEV

AWS Japan と BTM が11月20日に共同で公開した事例。TracisAI は Slack などから自然文で依頼すると、CloudWatch Logs と運用中の DB を調べて数十秒〜数分で結果を返すエージェントで、2026年6月に AWS Marketplace で提供を始めた。当初は顧客の VPC 内の ECS で動かしていたが、ECR からのイメージ取得経路が顧客ごとに違い、非エンジニア向けの製品なのにネットワークの準備でつまずくことが多かった。常時起動のコストも課題だった。AgentCore Runtime に移すと、VPC 内に置くのは IAM で呼び出し元を絞った Lambda だけになり、実際に使った CPU とメモリの秒単位課金になった。Gateway・Identity・Memory との連携による拡張性も決め手になったという。

  • CONSULT国内の中堅 SI が自社のエージェントを Marketplace で外販し、基盤を作り直した経緯として、同様の製品化を考える顧客に紹介できる。
  • DEV顧客 VPC にコンテナを置く方式より、VPC 外のマネージド実行と IAM で絞った VPC Lambda の組み合わせのほうが導入が楽だった、という具体的な知見。
