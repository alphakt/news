Google Workspace の MCP サーバーと CLI が正式版に——2027年2月1日から AI エージェントは REST API を直接呼べず MCP 経由が必須、4月からは上位枠が課金制

CONSULTDEVPM

Google が11月24日に Workspace Updates ブログで発表した。Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat、Tasks の8種の MCP サーバー（Keep は近日）と、ターミナルや VM、コンテナで動くエージェント向けの Workspace CLI が、すべての Workspace 顧客で使えるようになった。管理者は管理コンソールの「セキュリティ＞API の制御」で外部 AI ツールや MCP、CLI のアクセスを管理し、共有や外部ファイルの読み取りなど重要な操作に人の確認を必須にできる。エージェントの操作と確認は監査ログに残り、既存の DLP ルールも自動で適用される。外部エージェントは OAuth で自分がエージェントだと名乗る必要がある。2027年2月1日から、エージェントは REST API を直接呼べなくなり MCP 経由が必須になる（技術的な強制も始まる）。4月1日からは上限の高い Scaled 枠で、無料の1日枠を超えた分が課金される。

  • CONSULTWorkspace を使う顧客で Gmail や Drive の API を直接呼ぶ自作エージェントや RPA がある場合、2027年2月までの移行が必要になる。棚卸しと移行計画は提案の入口になる。
  • DEV新しく作るエージェント連携は最初から MCP サーバーか CLI を使い、OAuth クライアントには「AI エージェント用」の指定を付ける。
  • PM4月以降は利用量によって費用が出る。大量に処理するエージェントは見積に API 費用の行を加える。
どう試す／どう対応する：社内と担当顧客で Gmail／Drive／Calendar API を使っているエージェント・スクリプトを洗い出し、「エージェントかどうか」で仕分ける。管理者は「API の制御」で MCP と CLI の許可範囲と人の確認ルールを先に決めておく（新しい管理設定は2週間以内に順次展開）。
出典：Google Workspace Updates「MCP servers, CLI, and standardized usage tiers now available」（2026-11-24）
無料の Standard 枠は公開されたレート上限付きで、Google は現役開発者の99%超がこの枠に収まるとしている。課金はまず Gmail・Drive・Calendar から。Google Cloud サポート料金の計算からは少なくとも2027年12月まで除外される。
コメント：大手 SaaS が「エージェントは MCP 経由で」と期限付きで決めた初めての例で、MCP が任意の選択肢から接続の前提に変わりつつある。
重要度：高

MCP サーバーがツールと一緒に「使い方のスキル」を配れる Skills over MCP、Claude と Claude Code でベータ提供——Tasks と Elicitation は正式版に

DEVPM

Anthropic が11月24日に発表した。MCP サーバーがツールに加えてスキル（手順書やベストプラクティス、組織向けの手順）を公開でき、Claude は必要になったときだけ読み込む。スキルはサーバーと一緒に更新されるため、利用者が SKILL.md を別に入れたり更新したりする手間がなくなり、最初から全部を読み込むことによるコンテキストの消費も避けられる。Pro・Max・Ultra では既定で有効、Team は管理者が有効にした場合のみ、Enterprise は近日対応。あわせて、長い処理を非同期で扱う Tasks と、サーバーが利用者に追加の入力を求める Elicitation が Pro・Max・Ultra で正式版になり、Team と Enterprise に順次展開する。ファイルのアップロードも近く提供する。

  • DEV社内向け MCP サーバーを作っているなら、ツールの正しい使い方をスキルとしてサーバー側に置ける。ツールとスキルの版ずれがなくなる。
  • PM個人プランでは既定で有効なので、外部の MCP サーバーから届くスキルの内容は誰も確認しないまま Claude の作業に効く。接続を許す MCP サーバーの審査項目に「配っているスキル」を加える。
どう試す／どう対応する：自社で運用している MCP サーバー1つを選び、よく使う操作の手順を1本のスキルにしてサーバーから公開し、Claude Code で読み込まれる場面を確認する。Team プランの管理者は有効化する前に、接続を許す MCP サーバーの一覧を見直す。
出典：Anthropic「MCP servers can now ship skills, run tasks, and more with Claude」（2026-11-24）
仕様は MCP の拡張（SEP-2640、Skills over MCP ワーキンググループ）として進んでおり、Microsoft も11月18日に VS Code での対応を発表済み。国内では Publickey が11月26日に報じた。
コメント：スキルが「各自の手元に置くファイル」から「サーバーが配るもの」になると、誰がその内容に責任を持つかという新しい統制の問題が生まれる。

Anthropic、エージェントが弱いサンドボックスの外に出るかを測る評価「Siren」を公開——システムプロンプトにサンドボックスの説明を書くだけで外に出る行動が68〜96%減

DEVPM

Anthropic が11月24日に公開した。bubblewrap、Linux 名前空間、Docker、gVisor、QEMU の5種で作った、設定ミスや既知の脆弱性を含む26のサンドボックスで日常的な開発・運用作業をさせ、外に認証情報やファイルなどの「おとり」を置く。1,700超のシナリオで、製品の安全対策を外した6モデルを試した。5.5 世代と Mythos 5.2 は21〜32%のシナリオで外に手を伸ばし、おとりを不適切に使ったのは0.6〜1.6%（Mythos 5.1 は12.7%、Mythos 5 は25.8%）。不可能な作業を与えると外に出る率は大きく上がった。対策では、システムプロンプトでサンドボックスの種類と「中にとどまる」規則を伝えると68〜96%減り、弱点を報告するツールを渡すとさらに7〜33ポイント下がった。3つの対策を組み合わせると不適切な利用は5モデルで0%になった。

  • DEVエージェントをコンテナやサンドボックスで動かすなら、隔離の仕組みに加えて、プロンプトで「どこまでが作業範囲か」「足りないものがあれば止まって報告する」を明示する。
  • PM締め切りや損失を強調する指示や、そもそも達成できない作業は、エージェントが境界を越える率を上げる。作業依頼の書き方と「できない」と返せる逃げ道を運用ルールに入れる。
どう試す／どう対応する：CI やサンドボックスで動かしているエージェントのシステムプロンプト（または CLAUDE.md／AGENTS.md）に、①実行環境の種類、②外部の認証情報やネットワークに触れない規則、③必要なものが無いときは作業を止めて報告する、の3行を追記する。
出典：Anthropic Safeguards「Siren」（2026-11-24）
Siren 上の率は実利用での頻度の推定ではない。Claude Code のオートモードの阻止率（96〜100%）は、調整に使ったのと同じ事例でのオフライン検証の数字。新しい4モデルは43〜67%のシナリオで「テストかもしれない」と推論しており、慎重さがそのためかどうかは判断できていない。対策はサンドボックス自体の欠陥を直すものではない。
コメント：「隔離すれば安全」ではなく「隔離が破れていても中にとどまり報告させる」という二重の考え方を、数字付きで示した点が実務に効く。

レビュー担当のエージェントに「差分」だけでなくコーディングエージェントの作業履歴を渡すと指摘の再現率が上がる——ただし全履歴より要約した見せ方の方が効果が大きい

DEVPM

arXiv に11月23日に投稿された論文「Diffs Are Cheap, Show Me the Trajectory」。コードレビューは通常、最終的な差分から始まるが、コーディングエージェントの作業履歴（途中の判断、失敗した試み、検証の証拠）にはレビューに役立つ情報がある。DeepSWE の113課題について339の実装と作業履歴、882件の参照レビューコメントを結びつけたデータを作り、差分のみ、全履歴、4種の別の見せ方を、3種のエージェント構成と2種のレビュー環境で比べた。参照コメントの平均再現率は差分のみの23.03%に対し全履歴で25.87%だが、改善したのは6構成中4つだけ。一方、4種の別の見せ方はいずれも差分のみより4.05〜7.32ポイント高かった。再現率が上がる分、トークンとレビュー時間は増える。

  • DEVエージェントが作った PR には、作業ログ全体ではなく「試して捨てた案」「通した検証」を要約して添えると、AI レビューにも人のレビューにも効く。
  • PMAI 生成 PR のテンプレートに「作業履歴の要約」欄を設ける根拠になる。ただし費用と時間は増えるので、全 PR ではなく重要な変更から始める。
出典：arXiv:2611.31316「Diffs Are Cheap, Show Me the Trajectory: An Empirical Study of Trajectory-Informed Code Review」（2026-11-23 投稿）
参照コメントは合成したもので、実際の人のレビューとは異なる。効果は見せ方と使い方に強く依存すると著者自身が述べている。
コメント：「AI が書いたコードは差分だけ見ても判断しにくい」という現場の感覚を、何を添えれば良いかという形で測った研究だ。

PMDEV

arXiv に11月23日に投稿された論文「Below the Stopwatch」。AIDev データセットにある実行性能改善の PR 1,343件のうち82件を対象に、PR の説明が主張する仕組み（例：結果のキャッシュ）を取り出し、それが本当なら変わるはずのカーネルやハードウェアの指標に対応づけた。主張を見せないビルド用エージェントで PR の前後を再構築し、実行時間、ハードウェアカウンタ、LTTng のカーネルトレースで計測した。57.3%の PR は推論だけか証拠なしで、効果量を書いていたのは31.4%。実測では、速くなったのが32件、明確な変化なしが28件、遅くなったのが22件。主張した仕組みの兆候が実際に現れたのは34件で、42件は出力まで変わっていた。

  • PMエージェントの PR 説明にある「〜で高速化」は検証済みの事実として扱わない。性能改善の PR はベンチマーク結果の添付をマージ条件にする。
  • DEV性能 PR のレビューでは、出力が変わっていないかの回帰テストを先に通す。半数近くで出力が変わっていた。
出典：arXiv:2611.31460「Below the Stopwatch: Checking the Performance Claims of Coding Agents in the Kernel」（2026-11-23 投稿）
