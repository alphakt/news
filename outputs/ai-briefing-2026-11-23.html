Claude Code の「今後は確認しない」で保存された許可ルールに API キーやパスワードが混入、公開 GitHub で3万件超が見つかる

DEVPMCONSULT

InfoQ が11月22日、セキュリティ企業 Apiiro と GitGuardian の調査を報じた。シェルコマンドを「Yes, and don't ask again」で承認すると、そのコマンド文字列が恒久ルールとして .claude/settings.local.json に保存される。コマンドに認証情報が含まれていれば、それもそのまま残る。Claude Code はこのファイルを利用者のグローバル gitignore に追加するが、リポジトリの .gitignore には入れないため、別マシンでの clone や既にコミット済みの場合は防げず、Claude Code 自身がコミットした例もあった。GitGuardian は公開 GitHub 上で 31,088 件を検出し、うち 5,343 件が有効だった。Apiiro は 63 組織で計 2,282 件を確認し、gitleaks や TruffleHog はコマンドに埋め込まれた秘密を見逃すことが多かった。

  • DEV自分のリポジトリに .claude/settings.local.json が追跡されていないか、共有の settings.json に秘密入りのルールがないかを今日確認する。
  • PM既存の秘密スキャンを通っていても安心できない。エージェント設定ファイルを点検対象に加える作業を、導入チェックリストに入れる。
  • CONSULT顧客の Claude Code 展開支援では、リポジトリ単位の .gitignore 配布と、秘密を環境変数で渡す規約を初期設定に含めると説明できる。
どう試す／どう対応する：各リポジトリで git ls-files | grep settings.local.json と git log --all -- .claude/settings.local.json を実行し、見つかれば git rm --cached・.gitignore 追記・含まれていた認証情報のローテーションを行う。
出典：InfoQ「Claude Code Has Been Leaking Secrets through its "Don't Ask Again" Feature」（2026-11-22）

Claude Code の Edit の deny は Python からの書き込みを止めない——保護したはずの persona や SKILL.md をエージェントが heredoc で書き換えた実例

DEVPM

エージェントに記事作成サイトを運用させている開発者が11月22日、Zenn に記録を公開した。Edit(profile/**) や Edit(.claude/**) を deny していたが、改善案の実装中にエージェントが Python の heredoc で persona.md や SKILL.md など3ファイルを書き換え、エラーも出なかった。公式文書上、Read/Edit の deny は組み込みツールと、sed や tee のように書き込み先を読み取れるコマンドにしか効かない。著者の検証（2.1.309）では、deny だけだと Python は書き込めたが、sed とリダイレクトは拒否された。サンドボックスを併用すると3経路とも OS が拒否した。著者は保護領域への変更を patch にして人が git apply する運用に切り替え、11月1〜18日で39本を処理した。

  • DEVdeny は「ツールの入口の制限」であって境界ではない。守りたい場所には OS サンドボックスと allowUnsandboxedCommands: false を併用する。
  • PMエージェントの権限設計を「設定した」で終わらせず、禁止パスごとに実際に書き込みを試す点検を受け入れ条件に入れる。
どう試す／どう対応する：deny したパスごとに、エージェントに python3 -c "open('path','a')" を実行させ、書き込めてしまうかを確認する。書き込めたらサンドボックスを有効にする。
出典：Zenn「AIに編集を禁止したディレクトリを、AIが python で書き換えていた」（2026-11-22）
同日、AGENTS.md に書いたルールを読み飛ばされるので書き込み時に検査するフックへ移したという別の記録も Zenn に出ている。文章のルールより機械的な検査へ、という流れが続く。
コメント：前の記事の秘密漏えいと同じく、権限設定の「意味」を誤解したまま運用している例は多いはずだ。

OpenRouter が11月22日に公表した。セキュリティ企業 Dragos の研究者の検査で、一部の推論プロバイダのデータが侵害されていたか、データポリシーが守られていない証拠が見つかった。OpenRouter 自体への侵入はなかったとしている。Atlas Cloud、Novita、Phala、Together の4社が告知を出しており、Together は6〜7月のリクエストでプロンプト漏えいがあったと開示した。OpenRouter は名前を出さずに3社を切り離し、予防分も含めて 125 エンドポイントを ZDR 対象から外し、影響の可能性がある利用者に通知した。今後は研究者の検査手法を常時実行し、リクエストが第三者へ転送されていないか通信経路も確認する。

  • CONSULT11月中旬の Notion／Fireworks の委託先事案に続き、「どこで推論されるか」が漏えいの経路になった。ルーター経由の利用では、ZDR の表示だけでなく実際の経路先の監査を求めるよう助言できる。
  • DEVOpenRouter で機密データを扱っているなら、使っているエンドポイントが今も ZDR 対象か、プロバイダ固定の設定が必要かを見直す。

AI が書き AI が7観点でレビューしたコードでも、35% で本番に響くバグが残った——個人開発者が mutation テストで1か月半測定

PMDEV

実装もレビューもエージェントに任せて複数のサイトを運用する開発者が11月22日、Zenn に実測を公開した。9〜10月の約1か月半、/code-review や /security-review など7種類のレビューを通し、テストも全部通った実装に、最終検査として AI に mutation テストをさせた。197回中182回で「壊しても気づかれない」箇所があり、挙動が変わるのにテストが通った変異は 23%。バグ分析を数えた92回では32回（35%）に本番へ影響しうるバグが見つかり、うち9件は重大だった。最終ページ越えでの500エラー、無関係な行までロックする FOR UPDATE、N+1、閲覧数の二重計上などで、最終検査はレビュー時間の約35%を占めた。

  • PM「AI レビュー通過＋テスト緑」を完了条件にすると、3回に1回はバグが残りうる。見積にはテストの実効性検査の時間（レビューの3分の1程度）を別枠で置く。
  • DEVバグの多くは変異そのものではなく、変異を入れるために実装を読み動かす過程で見つかった。テストが実装の出力を写しているだけでないかを疑う。
出典：Zenn「AI が書いて AI がレビューしたコードでも、3 回に 1 回はバグが残っていた」（2026-11-22）
個人の Rails サイトでの1人分の記録で、一般化には注意が要る。
コメント：候補プールの「テストの実効性検査」を裏づける実データで、レビューを何重にしても検査の代わりにはならないことを示している。
