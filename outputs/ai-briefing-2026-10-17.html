重要度：高

Claude Codeチームが自分たちのコードレビュー体制を公開——「人間のレビュー時間を最小化」しつつ、リスクに応じて承認者を0〜2人に変える

DEVPMCONSULT

Anthropicは、Claude Codeのコードの約9割をClaudeが書く中で、どうレビューしているかを公式ブログで説明した。方針は「リバートや障害を増やさない範囲で、人間のレビュー時間を最小にする」こと。PR前にClaude自身がテスト・ビルド・lintを回し、フレッシュなコンテキストのサブエージェントが差分を見る。PRごとに複数のエージェントがバグを探し、別の検証エージェントが投票した指摘だけを投稿する。バグ・セキュリティ指摘が未解決ならマージをブロックし、人間の承認は低リスク0人、中リスク1人、高リスク2人で、機微なパスは必ず人が見る。6〜9月でマージPRは2倍超、リバート率は4割超低下し、PRにつく実質的コメントの割合は16%から54%に上がった。モノレポは1日約2,500件から3万件超の変更に増えたという。数値はAnthropic自身の社内データである。

どう試す：自社リポジトリで「変更パスごとのリスク区分（承認0/1/2人）」を CODEOWNERS とブランチ保護に落とし、AIレビューの未解決指摘をマージ必須チェックにする。まず1リポジトリで、リバート率とレビュー待ち時間を2週間計測する。
  • DEV「人が全行を読む」を前提にせず、事前検証・AIレビュー・必須CI・リスク別承認の層で品質を担保する具体的な型として、そのまま設計に使える。
  • PMレビュー待ちがボトルネックになる前に、承認者数をリスクで変える運用と、リバート率・収束ラウンド数（5回以上は8.9%から1.5%）という指標を計画に入れられる。
  • CONSULT「AIが書いたコードは誰がどこまで見るか」というクライアントの定番の質問に、実データ付きの参照事例として答えられる。ただし社内数値なので自社環境での再現は別途必要。
出典： claude.dev Blog「How the Claude Code team does code review」（Addy Osmani ほか、2026-10-15）
数値（PR数・リバート率・コメント率）はAnthropicの社内集計で、第三者検証はない。
コメント：「読む量を減らす」のではなく「読む場所をリスクで選ぶ」という整理が、今週のレビュー関連の話題の中で最も実装に落としやすい。
重要度：中

Cursorのクラウドエージェントが「Canvas」を作れるようになり、環境の管理用API（ベータ）と最大300リポジトリの環境にも対応

DEVPMCONSULT

Cursorは10月16日の更新で、クラウドエージェントの3点を発表した。（1）エージェントが作業の一部としてインタラクティブなCanvasを作成でき、完成したものはリンクでチームに共有できる。（2）クラウドエージェントが動く環境を、プログラムから作成・管理できるEnvironments APIをベータで提供する。（3）1つの環境で最大300リポジトリを扱え、大規模な環境の読み込みが5倍速くなった。変更履歴のページには、これらがどのプランで使えるかの記載がない。Canvasは調査結果や設計案を、コードの差分とは別の「読める成果物」として渡す用途に向く。複数リポジトリにまたがる改修を1つのエージェント環境で扱えるようになる点も、業務システムの保守では実務上の意味がある。

  • DEV複数リポジトリにまたがる変更や調査を、環境を共有したままクラウドエージェントに任せる前提で作業を分けられる。APIで環境を用意すれば、チーム標準の環境を揃えやすい。
  • PMエージェントの成果物が差分以外にも出てくるため、レビュー対象に「Canvas」を含めるかどうかを、運用ルールとして先に決めておく必要がある。
  • CONSULTクラウド型エージェントの環境管理が自動化できるようになった点は、導入時の「環境統制をどう標準化するか」の提案材料になる。プランと料金は未確認なので提示前に確認する。
出典： Cursor Changelog「Cloud agent canvases and environments」（2026-10-16）

AnthropicがMETRの評価チームを社内に常駐させ、従業員並みのアクセスを付与——公表の拒否権はなく、伏せ字化の要請のみ

CONSULTPM

Anthropicは10月15日、独立評価機関METRの6人に、社内の端末・オフィス・社内ツールへの従業員並みのアクセスを与えたと発表した。範囲は同社のリスク評価チームとおおむね同等で、顧客データ、秘匿特権のある通信、モデルのアーキテクチャ情報などは対象外である。METRはAnthropicのリスクレベル、インシデント、運用についての分析を公表でき、Anthropicは公表を拒否できない。事前に定めた区分の情報について伏せ字化を求められるだけで、METRはその妥当性についても見解を示せる。評価機関との連携は3段階で設計されており、METRは最上位の第3段階にあたる。第1段階では範囲を絞った調査で、公表にAnthropicの承認が要る。同社の報告にはない第三者の見解が出ること自体が、今回の変化である。

重要度：中

コード品質が高いほどAIレビューのトークン費用は下がる——エージェント作成の465PRで、CodeHealth 1点あたり3.5〜6.1%低下（ただしファイルサイズの影響を除くと消える）

PMDEV

Heander、BorgらはarXivに、コード品質指標CodeHealthがAIエージェントのレビュー・修正にかかるトークン数を予測するかを調べた事前登録研究を投稿した。AIDevデータセットの246リポジトリ、エージェントが作成した465件のPRに、3種類のLLMで5エージェント構成の固定パイプラインを実行している。3モデルすべてで、CodeHealthが高いほどトークン費用は低く、1点あたり3.5〜6.1%低い。PRの規模では説明できなかった。事前に登録した3つのコードの臭いのうち2つが修正費用を予測し、差は主にレビュー段階で出た。品質の低いコードではエージェントが反復を増やすが、コメント数は増えない。一方で、対象ファイルのサイズで調整すると関連が吸収され、著者はファイルサイズによる媒介と解釈している。

  • PMAI活用の費用見積に「対象コードの健全性」を入れる根拠になる。劣化したコードに対するエージェント作業は、トークン費用が膨らむ見込みで積む。
  • DEV大きく肥大化したファイルを分割すると、人にもエージェントにも読みやすくなり、レビュー費用が下がる可能性がある。ただし因果は確認されていない。
出典： arXiv:2610.21914「CodeHealth Predicts the Token Cost of Agentic Code Review」（2026-10-15）
観察研究で、因果は示されていない。ファイルサイズで調整すると効果が消える点に注意。
