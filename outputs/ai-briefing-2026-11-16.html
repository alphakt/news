Claude Code の Stop フックを自作したら、1セッションで差し戻しが1,314回・約16.5億トークンに——バックグラウンド処理の「待ち」を考慮しないフックが、約7.5秒おきのループを3時間続けた

DEVPM

Zenn の記事（11月15日）は、作業が終わるまで Claude Code を止めないよう、/goal を使わずに Stop フックを自作した結果を報告している。フックは合格の記録や CI の結果が欠けると作業に差し戻す。ところが、裏でテストを走らせて待つしかない状態で止まろうとするたびに差し戻されるループになった。計測は Opus 5.5 の1セッションで、差し戻し1,314回・約3時間、コンテキストの読み直し2,736回（1回約60万トークン）、合計約16.5億トークン、API 定価換算で約335ドル。著者によると、8回連続の差し戻しで打ち切る公式の安全装置は、間にツール呼び出しがあると回数が数えられず、効かなかった。

  • DEVStop フックで「未完了なら差し戻す」を書くときは、差し戻しを1回に限る。著者は公式文書が勧める形として、フックの冒頭に if (input.stop_hook_active) process.exit(0) を入れて解決した。
  • PM費用の大半は新しい出力ではなく、長いコンテキストのキャッシュ読みだった。無人で長時間走らせるエージェントには、セッション単位の使用量の上限か通知を用意する。
どう試す／どう対応する：チームのリポジトリと個人設定にある Stop フックを洗い出し、(1) stop_hook_active を見て2回目以降は通しているか、(2) バックグラウンドのコマンドが動いている間に差し戻していないか、を確認する。「絶対に止めない」をやめ、判定を通らないコードは push 時のフックで止める構成に替えるのが著者の結論。
出典：Zenn「/goalを使わずStopフックを自作したら、Claude Codeが止まらず使用量が増え続けた」（2026-11-15）
個人による1セッション分の計測。Max 5x プランでは週の利用枠が「体感で約2割」減ったとしており、これは計測値ではない。最初に試した「最長10分待ってから差し戻す」はループが遅くなっただけだった。安全装置の挙動は著者の説明で、本簡報では公式文書と照合していない。
コメント：「止めない仕組み」は、止まるべき場面を定義しないと費用の穴になる。完了判定はエージェントの外（push や CI）に置くほうが安全だ。

Zenn の記事（11月15日）は、サブエージェントへの委任手順をまとめた Skill を、あり・なしで比べた。Skill は4点を指示する。任せてよい仕事を、独立して並列にできるもの・結論だけが要る調べ物・別視点のレビューに限る。依頼文に目的、機械で判定できる終了条件、検証コマンドを書き、テストの削除・skip・期待値の緩和を禁じる。報告は入力の一つとして扱い、diff を読んで終了条件を自分で測り直す。架空の3場面を各3回試した結果は、34ファイルの置き換えで 3/24 → 18/24、夜間の lint エラー解消で 6/21 → 15/21、読み取り専用の調査で 11/15 → 12/15 だった。

  • DEV子エージェントの報告を信じず、終了条件を親が再実行して確かめる、という手順を Skill として配れる。npx skills add itoken-lab-jp/skills -g --skill delegating-work で導入できる。
  • PM確認の手順が増えるぶん往復も増える。試験では Skill ありの6回中4回が10往復の上限に達した。品質と所要時間の交換条件として見積もりに入れる。
出典：Zenn「サブエージェントの『すべて通りました』を、AI に確かめさせる Skill」（2026-11-15）Skill の説明（GitHub）

ITmedia ビジネスオンラインは11月16日、メルカリのエンジニアリング責任者とデザイナーへの取材記事（全3回の第1回）を掲載した。生成 AI の導入で、1〜2日かかっていたアプリの画面や試作品の制作が数十分に縮んだという。体制も変えた。フロントエンド、バックエンド、iOS、Android、Web と専門ごとに分かれていたチームを解き、1〜3人の少人数で画面から裏側の仕組みまで作る形に移している。一方で、多数の画面にまたがる変更を AI で一度に行えるようになり、人によるレビューと品質管理を保つのが難しくなった。人が関わる箇所と AI に任せる箇所を決め直しているという。

  • CONSULT「AI で速くなった後、何が詰まるか」を国内の大手が自分の言葉で語った事例。開発組織の再設計を提案するとき、職種別から少人数フルスタックへの移行例として引用できる。
  • PM制作が数十分になると、律速はレビューと品質保証に移る。工数の見積もりは「作る時間」ではなく「確かめる時間」を軸に組み直す必要がある。
  • DEV画面から裏側まで1人で触る前提になる。余白の規則に沿った部品づくりのような繰り返し作業は AI に任せる、という分担が紹介されている。

キーマンズネットは11月16日、オートバックスセブンの移行事例を掲載した。同社は2032年度に売上高5000億円（2022年度は2362億円）を掲げる。オフィスツールのライセンス更新で費用を見直した際、Google Workspace に Gemini などの生成 AI 機能が追加費用なしで含まれていたことが決め手になった。移行当初は従業員の約50%が従来ソフトの継続を望んだ。法務の契約書、経理の帳票、営業の複雑なマクロ計算には個別に配慮し、従来ソフトに残す業務は約25%とする計画。相談窓口を置き、DX 推進組織 ABDi が現場を支える。報告資料の作成は30分〜1時間から2〜3分になった例があるという。

  • CONSULT生成 AI の全社導入が、AI 単体の投資判断ではなく「オフィススイートの更新」として決まった例。ライセンス更新の時期が近い顧客には、AI 機能込みの総費用で比べる提案ができる。
  • PM全部を移さず、約25%は従来ソフトに残すと最初に決めている。マクロ資産の棚卸しと「残す業務」の線引きを、移行計画の最初の成果物にする。

取材記事で、同社の発表文ではない。対象人数、移行の日程、契約プランは記事に記載なし。時間短縮は記事中の一例で、全社の実測値ではない。店舗システムの仕様書やマニュアルを Gemini Notebook に集め、異動者や新入社員の立ち上がりに使う活用も紹介されている。
