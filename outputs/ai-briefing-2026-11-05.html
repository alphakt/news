Zenn の検証記事（11月5日）は、同じモデル・同じ20件の非公開テストで、MCP ツールの渡し方を2通り比べた。A は廃止予定やおとりを含む32個のスキーマを毎ターン送る方式、B は軽量な search_tools だけを最初に載せ、必要な2個を後から取り込む方式である。累計の入力トークンは79,773から5,844（−92.7%）、推定 API 費用は約0.074ドルから約0.011ドル（−84.8%）、所要時間は37.0秒から19.1秒に減り、おとりツールの誤呼び出しは2回から0回になった。独立テストの合格は両方式とも20/20。ただし1タスク・1回の実行で、ばらつきは示されていない。著者はツールが約10個を超えたら遅延読み込みを検討し、廃止ツールは検索層で除外するよう勧める。

  • DEV自分のエージェントに接続している MCP ツールの数とスキーマ分のトークンを数え、10個を超えるなら検索経由の遅延読み込みに替えるだけで、毎ターンの固定費を削れる可能性がある。
  • PMトークン費用の統制は上限設定だけでなく「何を毎回送っているか」の棚卸しから始められ、ツール定義の整理を低コストの改善項目として計画に入れられる。

InfoQ は11月4日、小説投稿サービスの Inkitt が小さく低リスクな変更を、タスク受付からテスト待ちのドラフト PR まで自動化した事例を報じた。起動は Slack、Linear、他のエージェントからの API 呼び出し。イベント駆動のオーケストレーターが使い捨てのエージェント用コンテナを動かし、仕様・実装・検証・CI 失敗の修復・マージ競合の解消を別々の段階として扱う。各実行は DB に保存され途中から再開できる。エージェントのコンテナには短命のトークンしか渡さず、Slack や Linear の資格情報は持たせない。検証・修復・競合解消は各2回まで、DB マイグレーション、認証、決済、CI 設定、パッケージの追加更新を含む作業は拒否し、PR はドラフトのまま人が承認する。

重要度：中

AI の「完了しました」を読まない設計：仕様から検証可能な主張を抽出し、人が承認し、終了コードで機械判定する spec-gate（Zenn）

DEVPM

Zenn の記事（11月5日）は、AI が書いたコードが自然言語の仕様に沿うかを判定する自作ツール spec-gate を紹介する。仕様とコードを直接比べず、仕様から「主張」（入出力例や性質）を AI に複数回抽出させ、一致度（3/3 など）を付けて人が承認・却下・曖昧に分類する。承認時に仕様文の hash を記録するため、仕様が変わると stale になって再承認が要る。検査は機械が行い、結果は pass／unapproved／stale／fail／unverified の5種で、エージェントの自己申告は判定に使わない。機械検査が無い主張は合格に数えず人の確認に回す。設定例では fuzz を200回、変異テストで80%以上の注入バグを検出できない計画は確定させない。

  • DEVClaude Code のフックから終了コード2で修正を差し戻す構成は、「完了」報告を読まずに品質ゲートを置く実装例として自分の環境にも写せる。
  • PM「機械検査が無い主張は合格に数えない」という扱いは、AI 成果物の受け入れ基準に未検証の項目を明示する運用の参考になる。
出典： Zenn「AIは嘘をつく前提で。仕様準拠を exit code で判定する『spec-gate』を作った」（2026-11-05）
個人の自作ツールで、合格率や欠陥検出数などの実測はない（数値は設定例）。著者表記が記事内の GitHub リンクと一致しない点があり、導入前にリポジトリ側を確認したい。
コメント：実測がない段階の設計案だが、「人が承認する主張」と「機械が判定する検査」を分ける考え方は11月2〜4日号のレビュー関連の話と一貫している。

DEVCONSULT

Simon Willison が11月3日の記事で、論文「Sparks of Weight-Space Programming」の実験1（ニューラルネットの生の重みだけを見て、学習したゲームを当てる）を、ローカルの Qwen 3.8 27B（Q4_K_M、約17GB、LM Studio）で追試した。ブレイクアウト用の重みでは Arkanoid 風のブロック崩しと88%の確信度で答え、パックマン用は「パックマン風の迷路」（72%）、ポン用はポン風（75%）と推定、フリーウェイ用は外れた。所要は約46分〜1時間超で、長いコンテキストとタイムアウトの延長が必要だった。各ゲーム1回の試行である。Kimi K3.1 Pro は OpenRouter 経由で約9分41秒、推論トークン19,493でブレイクアウトを当てた。Willison は論文の主張は誇張だと見ている。

  • DEV27B 級のローカルモデルで長い数値入力を扱うには、コンテキスト長とタイムアウトの設定が実用上のボトルネックになる点を押さえておける。
  • CONSULT「LLM が重みを読み書きする」という話題がクライアントに出た場合、元の実験は1回ずつの試行で、第三者から過大評価との批判もあると伝えられる。
