AWS が公式のローカルエミュレータ「AWS Emulator」を公開——コードは全行を数千の自律エージェントが書き、人は一行も書かずレビューもしていない。人が設計したのは仕様・忠実度テスト・マージ門だけ

AWS は11月11日、AWS の API を手元で再現するエミュレータを公開した。AWS アカウントなしでテストでき、Linux は RPM／Debian パッケージ、macOS と Windows は Docker で動かす。ライセンスは CC0。開発の仕方が異例で、AWS の技術者によれば、438の API モデルを受ける空のサーバーから始め、3つのエージェント群が1つのリポジトリで働いた。テスト作成役が実際の AWS で確かめた忠実度テストを作り、発見役がエミュレータで再生して不一致を起票し、修正役が1件ずつ直す。変更はビルド・コーディング規約・セキュリティ・忠実度の退行を調べるマージ門を通ったものだけが入る。数百のエージェントが並行し、1日に数千件を修正する。未対応の API はリポジトリの issues/things-that-do-not-work/ に公開されている。

  • DEVCI やエージェントの検証ループで、実 AWS を呼ばずに統合テストを回せる。コーディングエージェント用のスキルも AWS CLI から追加できる。
  • PM人のコードレビューを置かず「正解と照合するテスト＋自動の門」で品質を保つ大規模な実例。正解（実 AWS）が存在する移行・互換実装の案件ほど当てはめやすい。
  • CONSULT「AI だけで作ったソフトを公式製品として出す」事例として顧客に聞かれる。成立条件（機械的に照合できる正解があること）まで説明できるようにしておく。
どう試す／どう対応する：SQS や S3 など1サービスだけ使う既存の統合テストを、エンドポイントをエミュレータに向けて実行する。先に issues/things-that-do-not-work/ で使う API の対応状況を確かめる。

GitHub が「エージェントスキル」の実践ガイドを公開——SKILL.md を1つの原本にして Claude Code・Cursor・GitHub Copilot 向けに自動で包み直し、検証は別のエージェントに任せる

DEVPM

GitHub は11月12日、繰り返す開発作業をスキルとして書き、複数のエージェントで使い回す方法を実例で解説した。スキルは SKILL.md を中心とするバージョン管理されたディレクトリで、名前、何をするか、いつ使うか、何を確かめてどんな証拠を返すかを書く。原本は skills/*/SKILL.md に置き、パッケージ用スクリプトが Claude Code、Cursor、Copilot 用の設定ファイルを生成する。プロジェクト固有の名前やスキーマはスキルに書かず、別のマニフェストに分ける。例のデータ基盤ワークフローは7段階すべてに人の確認点を置き、スキーマ変更の前に承認を求める。検証は「自己検証は検証ではない」として別の検証エージェントが PASS／FAIL／PARTIAL を根拠付きで返す。

  • DEVチームで同じ説明を何度もエージェントにしている作業を、ツールを問わず使える形で持てる。パッケージの整合は CI（--check）で確かめる。
  • PMスキルは権限を与えない。ツール・認証情報・権限は環境側で別に用意し、エージェントごとに動作確認が要る点を計画に入れる。
どう試す／どう対応する：説明に飽きた定型作業を1つ選び、必要な入力・止まる地点・レビュー者に見せる証拠を SKILL.md に書く。2つ目のエージェントで動かして直す。

ラクス「AI でテストを約900本作ったら、レビューが重くなった」——約460行・約220分岐の処理に安全網を張る過程で、レビューが「AI の意図をたどる作業」に。基準を先に揃え、指摘をスキル化して解消

DEVPM

ラクスの開発者ブログ（11月12日）は、楽楽精算の伝票画面の表示処理（約460行、約220分岐）を作り直す前に、現状の振る舞いを固定するテストを AI で作った経過を報告した。4人が10の申請種別を分担し、1種別あたり約90本、全体で約900本近く。大枠は共有していたが、モックの組み方、アサートの書き方、粒度が揃っておらず、レビュー者はテスト1本ごとに分岐条件やモック設定をたどることになり、他種別への展開日程にも響いた。対策は2つ。1種別を基準に全員でレビューして方針を固めてから展開すること、レビュー指摘を4群の観点としてスキルにし、作業者が AI と自己点検すること。特に効いたのは、通っているのに何も保証していないテストの検出で、対象の分岐を消しても成功するかで見分ける。

  • DEVAI にテストを書かせる前に、モック・アサート・粒度の基準を1件の見本で決める。「分岐を消しても通るテスト」は機械的に点検する。
  • PM並行で量産してから揃えると手戻りが出る。「1件を基準化→横展開」の順を計画に組み、レビュー者の確認項目を絞る。

Martin Fowler「生成用語集（Generated Glossary）」——社内文書から LLM に用語と定義を下書きさせ、専門家が直してバージョン管理する。全社で1つにせず、文脈ごとに分ける

DEVCONSULT

Martin Fowler は11月12日、専門領域で LLM がうまく働かない原因を「社内の言葉が学習データにないこと」とし、用語集を作って渡す実践を紹介した。作り方は、文書・メール・チャット・会議の文字起こしを集め、LLM に用語の候補（特に、一般的な語を独自の意味で使っているもの）を挙げさせ、辞書形式の定義を下書きさせ、領域の専門家が誤りを直す。保守は、トークンを節約できる形で保存し、バージョン管理し、エージェントと人の両方で定期的に見直す。大きい用語集は用語とリンクだけ先に読み込み、定義は必要時に取得する。使い道は、生成するコードや文書の命名の統一、ハーネスでの用語チェック、社内用語を顧客向け文面に出さないこと。避ける語と代替、廃止語も記録する。

  • DEVCLAUDE.md／AGENTS.md に用語を書き連ねる代わりに、用語集を別ファイルにして必要時に引かせる構成の根拠になる。
  • CONSULT導入初期の成果物として提案しやすい。部門ごとに同じ語の意味が違うこと自体が、業務整理の材料になる。

フォーティエンスコンサルティング（旧クニエ）は11月11日、企業の AI ガバナンスの整備状況を診断するサービスの提供を始めた。総務省・経済産業省の「AI 事業者ガイドライン」を踏まえた独自の枠組みで、「組織・体制」「方針・ルール」「人材育成」「リスク管理」「データ・セキュリティ」「透明性・モニタリング」の6領域を5段階の成熟度で評価する。クイック診断は必要情報の確認後、最短1営業日で結果を示し、本診断は4週間から。成果物は領域別スコアのレーダーチャートと、優先度を付けた施策一覧。診断後は方針・体制の設計（2か月から）、規程・ガイドラインの制定やリスク確認プロセスの構築（3か月から）、ISO/IEC 42001 の認証取得まで支援する。料金は個別見積もりで、製造・流通・金融・公共など幅広い業界を対象とする。

  • CONSULT競合の「入口商品」の型（短期の無料に近い診断→本診断→規程整備→認証支援）が見える。自社の提案で領域の切り方と所要期間を比べる基準になる。
