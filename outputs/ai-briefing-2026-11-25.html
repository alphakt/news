CLAUDE.md／AGENTS.md の「依存ルール」の18%は書いた時点で既に破られていた——3,346 の OSS で 3,602 のコンテキストファイルを実コードと照合

DEVPM

arXiv に11月23日に投稿された論文。CLAUDE.md や AGENTS.md に書かれた構造の主張のうち、機械的に確かめられる2種類——フォルダやファイルを示す「パスの主張」41,090件と、許される import を定める「依存ルール」184件——を現在のコードと履歴で検証した。パスが見つからないのは約5%だが本当の誤りは推定2.2%で、README（3.5%）より正確だった。コードが動くと古くなった主張の61%は直され、多くは同じコミットで直る。一方、依存ルールは184件中33件（18%）が書いた時点で既に破られ、ほぼすべて破られたままだった。著者は「よい地図だが、規則集としては当てにならない」とまとめる。

  • DEVエージェントは文脈ファイルを正しいものとして読む。「理想の設計」を規則として書くなら、現状との差を明記するか、import の検査をリンタや CI に置いて規則と実態を一致させる。
  • PM文脈ファイルの保守は「パスの記述」より「規則の記述」に手を掛ける。レビュー項目に「規則がコードで守られているか」を加える。
どう試す／どう対応する：自分のリポジトリの CLAUDE.md／AGENTS.md から「〇〇は△△を import しない」型の規則を抜き出し、grep か依存解析ツール（例：import-linter、dependency-cruiser）で1本ずつ現状と照合する。破れている規則は直すか「目標」と書き換える。
出典：arXiv:2611.29916「Does the Agent's Map Match the Territory? Architectural Claims in AI Agent Context Files and Their Fit with the Code」（2026-11-23 投稿）
エージェントが関わったコミットは規則違反が約1.8倍（0.29%対0.16%）だったが、違反は計14件で統計的に有意ではなく、著者も「初期の兆候」としている。分析には LLM を使い、各段階を人が確認した。

重要度：高

claude mcp add --header の Authorization は画面では [REDACTED] でも設定ファイルには平文——--scope project ならコミット対象の .mcp.json に入る

DEVPM

Qiita に11月24日に投稿された検証記事（Claude Code 2.1.330、Codex CLI 0.171.0、ダミーキーで確認）。HTTP の MCP サーバーを --header "Authorization: Bearer キー" で登録すると、表示は伏せられるが値は平文で保存される。--scope project ではリポジトリにコミットする前提の .mcp.json に、既定の local と user スコープでは ~/.claude.json に書かれる。STDIO サーバーの -e API_KEY=... や codex mcp add --env（~/.codex/config.toml）も同様。~/.claude.json は所有者しか読めないが、ホームのバックアップやエージェントによる読み取りで漏れうる。著者はキー名らしき項目に直書きの値がある行を探す grep を1行で示し、${API_KEY} のような環境変数参照への置き換えを勧めている。

  • DEV画面で伏せ字になっていることは保存時の秘匿を意味しない。MCP の設定は環境変数参照で書き、.mcp.json をコミットする前に値を確認する。
  • PMMCP 導入手順書の登録コマンド例に直書きのキーがあれば差し替える。一度でも push したキーは履歴に残るので、失効と再発行を手順に含める。
どう試す／どう対応する：チームの各リポジトリの .mcp.json と各自の ~/.claude.json・~/.codex/config.toml を KEY／TOKEN／SECRET／Authorization で検索し、$ で始まらない値があれば環境変数参照に直す。コミット済みなら即失効する。
出典：Qiita「claude mcp add --header の Authorization は画面では [REDACTED] でも .mcp.json には平文」（2026-11-24）
個人の検証記事。ANTHROPIC_AUTH_TOKEN など一部の変数はリモートの url／headers では展開されないため、サーバー用のキーには別の変数名を使うよう著者は注意している。grep は X-Api-Auth のような名前を拾わない。
コメント：11月23日号の「今後は確認しない」で許可ルールに秘密が混入した件と同じ型で、エージェントの設定ファイルが新しい秘密の置き場になっている。

iFood、1万5千のリポジトリにエージェント作業を API で流す社内基盤を構築——2万5千回超を実行し、1回あたり平均約0.04ドル

OpenAI が11月24日に公開したブラジルの iFood の事例。社内の Remote Agents Platform は、プロンプトと環境の条件を REST API で受け取り、隔離したサンドボックスでエージェントを走らせ、結果をマージリクエストとして返す。リポジトリのクローン、スキルの読み込み、ブランチ作成、MR の発行は決定的な処理で行い、モデル（GPT-5.6 Luna）は間の作業だけを担う。出力は Structured Outputs の決められた形式で、成功か失敗かを判定する。最初の大口利用者は全リポジトリの脆弱な依存関係を検出・修正するセキュリティ製品で、移行後に修正の正確さと解消件数がともに2倍超になったという。累計2万5千回超、270億トークン超を消費した。

  • PM依存更新や規約チェックのような定型作業は「1回数セント」で見積もれる単位になった。人のレビュー工数の方が支配的になる前提で計画する。
  • DEV決定的な前後処理でモデルの担当範囲を狭め、出力を構造化して合否判定する設計は、大量のバッチ型エージェントを作るときの参考になる。
  • CONSULT多数のリポジトリを持つ顧客に「脆弱性修正の一括エージェント化」を提案する際の規模と単価の目安になる。

エージェントがデータベースで誤操作したとき被害を左右するのは「どれだけ壊れるか」より「どれだけ戻せるか」——4種の DB エンジンで 22 種の誤りを再現した事前登録型の実験

PMDEV

arXiv に11月23日に投稿された論文。第1層では、エージェントが犯しがちな22種の誤りを、4つのリレーショナル DB エンジン、5種の権限設定、2種の復旧設定でスクリプト的に再現し、エンジン固有の復旧訓練を874回行った。第2層では、4B〜12B の小型オープンモデル6種で動く最小限のエージェントに、危険を含む作業を9エンジンで9,468回させた。結論は、初期設定のままではエンジン間の差は被害の大きさより「何を取り消せるか」に表れるというもの。事前登録した7仮説のうち規則を満たしたのは3つで、うち2つは設計上ほぼ自明だったと著者は認めている。

  • PM本番 DB にエージェントを触らせる計画では、権限を絞るだけでなく、ポイントインタイム復旧などの取り消し手段と復旧訓練を受け入れ条件に入れる。
  • DEVDB 用ツールを設計するときは、操作ごとに「戻せるか」を分類して、戻せない操作だけ承認を挟む構成が検討に値する。
出典：arXiv:2611.30483「When an AI agent makes a mistake in a database, what decides the damage?」（2026-11-23 投稿）
使ったのは小型モデルのみで、最上位モデルのエージェントでの挙動はわからない。事後分析は探索的で多重比較の補正をしていない。
