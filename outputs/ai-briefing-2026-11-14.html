Claude Code に実験機能「Code Mode」——ツールを1回ずつ呼ぶ代わりに、Claude が JavaScript を書いて複数のツール呼び出しを1ステップで実行する。既定はオフで、組織単位で禁止もできる

DEVPM

Anthropic は11月12日公開の Claude Code v2.1.323 に Code Mode を追加した。通常は Bash・Read・Edit などを1回ずつ呼ぶが、Code Mode では Claude が JavaScript を書き、検索→編集→テストのような一連の呼び出しをまとめて実行して必要な結果だけ受け取る。多数のファイルへの同種の変更や、並列で走らせられるコマンドに向く。有効化は環境変数 CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1。各呼び出しには従来どおり deny／ask の権限規則と PreToolUse フックが効くが、auto モードの分類器は個々の呼び出しではなくコード全体を審査し、実行時に決まる値は見えない。

  • DEV繰り返しの多い作業で試す価値がある。書かれたコードは Ctrl+O の transcript で読める。コード自体を点検したい場合は REPL ツールに一致する PreToolUse フックを書く。
  • PM使えない構成が多い。Bedrock・Google Cloud・Microsoft Foundry・ゲートウェイ経由、ゼロデータ保持や HIPAA 構成の組織、-p・Agent SDK・VS Code パネル・デスクトップ・クラウドセッションは対象外。顧客環境で使えるかを先に確かめる。
どう試す／どう対応する：個人の検証用リポジトリで CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude を起動し、「全 Markdown のリンク切れを列挙」のような呼び出しの多い作業を流す。組織として止めるなら managed settings の env に同変数を "0" で入れる。
出典：Claude Code Docs「Run tool calls from code with Code Mode」Claude Code Changelog（v2.1.323、2026-11-12）
実験機能で、予告なく変更・削除されうると明記。Code Mode のセッションは Code Mode を有効にした端末でしか再開できない。翌日の v2.1.325 で Code Mode 関連の不具合が3件修正されている。トークンや速度の改善幅は公式文書に記載なし。
コメント：権限規則とフックは引き続き効くが、auto モードの審査単位が「呼び出し」から「コード」に変わる点は、運用ルールを決める側が押さえておきたい。

Thoughtworks「攻撃者は、ソフトウェアを作る AI ツールそのものを狙っている」——AI コーディングツール・拡張・MCP サーバーをサプライチェーンの一部として扱い、更新の固定・権限の縮小・開発端末の監視を求める

DEVPMCONSULT

Thoughtworks は11月13日、AI コーディングツール（アシスタント、エディタ、拡張、MCP サーバー）はソフトウェア供給網の一部であり、開発者の端末を取られるとソースコード・認証情報・配備の経路まで露出すると論じた。実例に、10月29日に Cursor のマーケットプレイスで Claude Code 拡張の改ざん版が約11時間配布され最大5,000人に影響しえた件と、Trivy や LiteLLM を狙った TeamPCP の攻撃を挙げる。対策は、検証済みバージョンの固定と段階展開、署名と来歴の確認、管理者権限の削除、開発と本番の分離、短命な認証情報、サンドボックス化、開発端末の監視。

  • DEV拡張と MCP サーバーの自動更新を見直す。SSH 鍵の変更、新しい自動起動、想定外の認証情報アクセス、不審なトンネルが監視対象として挙がっている。
  • PMツールの採用を「個人の好み」ではなく技術判断として扱い、開発ツールの侵害をインシデント対応手順に入れる。端末の完全初期化とリポジトリ・クラウドの監査まで想定する。
  • CONSULTAI 駆動開発の導入提案に「開発ツールの供給網管理」を1項目として入れる根拠になる。
どう試す／どう対応する：チームで使っている AI 拡張・MCP サーバーを一覧にし、自動更新の有無と、各ツールが触れる認証情報を書き出す。まず自動更新を止めてバージョンを固定し、更新は数日遅らせて適用する。
出典：Thoughtworks「Attackers are targeting the AI tools that produce our software」（2026-11-13）
新しい攻撃の報告ではなく、既知の事例を踏まえた整理と提言。Cursor の件は本簡報10月31日号で既報。TeamPCP の時期は記事に記載なし。
コメント：「AI ツールを入れるか」の議論は進んでも、「入れたツールの更新を誰が管理するか」は空白のままの現場が多い。
重要度：中

Thoughtworks が AI 開発ワークフローの評価基盤「SpecBench」を紹介——仕様・計画・分解の段階を足すと正しさは 92.25%→95.00% に上がるが、トークンは約4倍、時間は約2倍

PMDEV

Thoughtworks は11月13日、AI を使う開発ワークフローを同じ課題で走らせて比べる評価基盤 SpecBench を紹介した。実行ごとに成果物・実行記録・資源の計測を残し、振る舞いの正しさ、品質、過程、時間、トークン、推定費用を出す。対象はフロントエンド、バックエンド、フルスタック、コマンドラインの4場面。記事の実績値では、直接実装させる基準に対し、仕様・計画・分解を挟むワークフローは正しさが 92.25% から 95.00% へ上がり、4場面すべてで上回った。一方、平均時間は 83.74 分から 163.93 分、トークンは 450K から 1,782K、推定費用は 1.45 ドルから 2.25 ドルに増えた。

  • PM「仕様駆動にすれば良くなる」を、正しさ約3ポイントと費用・時間の増加の交換として説明できる。どの案件で割に合うかを判断する材料になる。
  • DEVワークフローを変えるときは、成果物の品質だけでなく過程と資源を同じ課題で測って比べる、という型が参考になる。
出典：Thoughtworks「SpecBench: A tool to evaluate AI-enabled software development workflows」（2026-11-13）
著者は、2つの結果は実行条件が同一とは限らない記述的な実績値だと断っている。既存コードのある案件（brownfield）は未対応。公開リポジトリや利用手順は記事に記載なし。
コメント：仕様駆動の効果を「感触」ではなく費用込みの数字で出した例は少なく、見積もりの議論に使いやすい。
重要度：中

研究「Termination Lag」——コーディングエージェントは正しい修正に早く到達しているのに止まらない。成功した実行の 38〜82% は最初の編集で正解、その後のステップが実行の3〜6割を占める

DEVPM

arXiv の論文（11月11日投稿）は、エージェントが最初に正しいパッチを作ってから実行を終えるまでを「termination lag」と定義して測った。5モデル、2つのエージェント枠組み、3つの SWE-bench 系データセットで、作られたパッチをすべてテストにかけた。成功した実行の 38〜82% は最初のコード編集の時点で正解だった。正解後のステップが成功実行に占める割合の中央値は、Qwen3-Coder で 35〜37%、Laguna-XS.2 で 54〜60%。その大半は検証とリポジトリの探索だった。1〜8% では、続けた結果として正しいパッチを自分で取り消し、最終結果が不正解になった。

  • DEV「いつ止めるか」はハーネス側で設計できる対象。テストが通った時点で止める条件や、停止判断を別の小さなモデルに任せる構成を検討する根拠になる。
  • PMエージェントのトークン費用の相当部分が「解けた後」に使われている可能性がある。費用削減はモデルの単価だけでなく停止条件でも効く。
出典：arXiv 2611.14960「Termination Lag: Coding Agents Solve Early but Stop Late」（投稿 2026-11-11）
査読前の論文。評価は SWE-bench 系のベンチマーク上で、正解かどうかをテストで判定できる課題に限られる。著者の所属は arXiv のページに記載なし。
コメント：決定モデルで停止判断を切り出す流れ（Jev など）に、測定値の裏付けが付いた形。
重要度：中

研究：OSS のメンテナーが「AI slop」と判定したプルリクエストを調査——AI 利用を自ら開示していたのは 14%、多くは理由の説明なしに3日以内に閉じられている

PMDEV

arXiv に公開された論文（11月11日投稿）は、フリー／オープンソースのプロジェクトでメンテナーが「AI slop」（AI で作られた低品質な投稿）と明示したプルリクエストを集め、出どころ、量、特徴、閉じられた理由を調べた。件数は2025年半ばから増え、2026年5月が最多だった。内容は追加が中心で、典型的には3日以内に閉じられている。投稿者が AI の利用を自分から開示していたのは 14%、メンテナーに問われてから開示したのが 1%。大半は理由を示されないまま閉じられるか、slop と印を付けられていた。著者らは初期段階の現象に対する探索的な研究と位置付けている。

  • PM外部や協力会社からの PR を受ける案件では、「AI 利用の開示」と「受け付けない基準」を先に文書化しておく。理由なしで閉じる運用は、投稿側の改善にもつながらない。
  • DEV自分が OSS に PR を出す側でも同じ。AI を使ったなら開示し、変更の意図と検証内容を添える。
出典：arXiv 2611.15159「An Empirical Study of Maintainer-Identified AI Slop Pull Requests in Free and Open Source Software Projects」（投稿 2026-11-11）
査読前の論文（12ページ）。対象はメンテナーが slop と明示した PR に限られ、見逃された低品質 PR や、質の高い AI 生成 PR は含まない。対象件数は要旨に記載なし。
コメント：Hono の外部 PR 受付停止（11月2日号）のような個別の動きを、データで俯瞰する最初の材料。

llama.cpp と ggml が v1.0.0 に到達——公開 C API の非互換はメジャー版の更新時だけ、というバージョン規則を明示

DEVCONSULT

ローカル LLM 実行の基盤である llama.cpp と ggml は11月13日、両ライブラリ（libllama、libggml）の v1.0.0 を公開した。以後はセマンティックバージョニングに従い、./include の公開 C API を壊す変更はメジャー版の更新時に限る。マイナー版は後方互換のある機能・バックエンド・対応モデルの追加、パッチ版は不具合修正とする。発表によれば対応するモデル構造は150種以上。ggml のバックエンドは動的ライブラリとして実行時に読み込める。配布経路は Docker、Debian、Homebrew、conda-forge、Winget などに広がった。

  • DEVllama.cpp を組み込んだ製品で、更新のたびに API の破壊を心配する必要が減る。依存バージョンの指定をメジャー版で固定できる。
  • CONSULTデータを外に出せない顧客へのローカル／オンプレ推論の提案で、基盤の安定性を説明する材料が1つ増えた。
出典：Hugging Face Blog「llama.cpp v1.0.0 : A stronger foundation for the local AI ecosystem」（2026-11-13）
v1.0.0 での具体的な非互換変更や移行手順は記事に記載なし。リリースページの確認が要る。
コメント：機能より「約束」の発表。ローカル推論を製品に組み込む側にとっては、この約束のほうが効く。
