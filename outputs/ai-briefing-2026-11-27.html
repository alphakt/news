重要度：高

AI レビュー担当の effort を上げると誤ったパッチを通す率は下がる——ただし Claude 5.5 系のどの設定でも、誤りの45%以上は「正しい」と判定された

DEVPM

arXiv に11月25日に投稿された論文。SWE-bench Verified の Django 課題でエージェントが書いた90件のパッチ（より厳しいテスト SWE-ABS で55件が誤り、35件が正しい）を、Claude 5.5 の Opus・Sonnet・Haiku にレビューさせ、effort の設定ごとに誤ったパッチを「正しい」とした率を測った。low から high に上げると、Opus は0.67→0.45、Sonnet は0.65→0.49、Haiku は0.78→0.51に下がった。Opus は medium でも high と比べて15ポイント以内の差に収まり、費用は20%少なかった（事前に決めた30%削減の目標には届かず）。Sonnet と Haiku は medium にすると費用が39%・51%減るが、精度が劣らないことは示せなかった。Haiku の high は Opus の medium の約8%の費用で済む。

  • DEVAI レビューを CI に入れているなら、effort を low のまま使うのは避ける。費用を抑えるなら Opus の medium が目安になる。
  • PMAI レビューを「合格の門番」にはできない。どの設定でも誤りの半分近くが通るので、人のレビューやテストを減らす根拠にしない。
どう試す／どう対応する：AI レビューを動かしている CI の設定で effort（推論量）を確認し、low なら medium 以上に上げる。あわせて、過去に人が差し戻した PR を10件ほど AI レビューに通し、何件を見逃すかを自社のコードで確かめる。
出典：arXiv:2611.33639「How Much Effort Does an AI Code Reviewer Need? Evidence from Claude 5.5 Models on Plausible-but-Wrong Patches」（2026-11-25 投稿）
対象は Django の90件のみ。誤りとされた55件のうち32件は、課題文が失敗したテストの内容まで求めていない可能性があると著者自身が述べている。
コメント：「AI に AI のコードを見させれば安心」という前提に、効く設定と効かない限界の両方を数字で示した研究だ。
重要度：中

「1行ずつのコードレビューはもう機能していない」——QCon SF で Aviator の CEO が、レビューを議論・意図の記録・不変条件・証拠など6つの層に置き換える方法を提案

PMDEV

InfoQ が11月26日に報じた QCon San Francisco 2026 の講演。Aviator の Ankit Jain 氏は、4,000超のチームを調べた Faros の9月の調査で75%超の PR が人のレビューなしでマージされていること、PR の中央値が約640行に増えたことを挙げ、レビューは「AI が書き AI が見て人が流し読みする」形だけのものになったと述べた。代わりに、①PR を出す前にエージェント同士で議論させ意見の割れた点だけを出す、②作業中に意図と受け入れ条件を記録して PR に付ける、③繰り返し出るレビュー指摘を担当チーム付きの不変条件にする（同社は1万1千件の指摘を64の不変条件にまとめた）、④緑のチェックではなく画面や通信記録などの証拠を出させる、⑤人は差分でなく判断を議論する、⑥責任をルールの持ち主に移す、の6層を提案した。

  • PM過去のレビュー指摘を集めて不変条件（自動チェックや CLAUDE.md のルール）にする作業は、AI 導入後の品質計画にそのまま入れられる。
  • DEVエージェントが書いたテストはエージェント自身の思い込みを含む。PR には画面やリクエストの記録など、実際に動いた証拠を添えさせる。
出典：InfoQ「QCon San Francisco 2026: How to Kill the Code Review」（2026-11-26）
講演者は関連製品を販売しており、9人のチームで PR が4倍、差し戻しが約40%減という数字は本人の申告。セキュリティ・認証・課金のコードは今も1行ずつ見ているという。インデックスのないクエリによる18分の障害はすべての層をすり抜けた。

コーディングエージェントの不要な編集を7,660件で実測——不要なコードは開発者並みかそれ以下だが、残った不要コードの89%は動作を変えていた

DEVPM

arXiv に11月25日に投稿された論文。GitHub Copilot CLI で18の先端モデルが課題を解決した7,660件の作業記録（SWE-bench Verified 6,728件、DeepSWE 932件）を、開発者のパッチと同じ方法で採点した。SWE-bench Verified では、余分な編集の61%はテストの追加、13%はドキュメントの追加。一方 DeepSWE では余分な編集の58%がコードだった。コードの必要度は SWE-bench Verified でエージェント0.887、開発者0.864と、18モデル中11モデルが開発者より不要コードが少なかった。ただし約11%のコードはなお不要で、その89%は動作を変えていた。DeepSWE では不要コードの少なさと解決率が逆相関した。手元のテストで刈り込むと不要コードの多くを除けるが必要なコードも削り（再現率67%、適合率46%）、エージェント自身に見直させると正確だが取りこぼしが多い（再現率36%、適合率66%）。

  • DEVエージェントの PR では「課題に関係ない変更」が動作を変えていないかを重点的に見る。自己レビューだけでは3分の2近くを見逃す。
  • PM難しい課題ほど解決率の高いモデルが余計なコードも書く傾向がある。解決率だけでモデルを選ぶと、レビュー量が増える。
出典：arXiv:2611.34875「How Much Do Coding Agents Over-Edit, and Why?」（2026-11-25 投稿）
ベンチマーク上の課題での結果で、企業の実コードでの割合は分からない。
コメント：「エージェントは余計なことをする」という印象を、量はそれほど多くないが中身が危ない、という形に分けて示した点が使える。
重要度：中

開発者体験（DevEx）のエージェント版「AX」——作業記録を明確さ・実行可能性・忠実さ・効率の4軸で採点すると、最も低いのは「実行可能性」、文脈に欠陥があるとトークンが平均91%増えた

DEVPM

arXiv に11月24日に投稿され、26日に公開された論文。コーディングエージェントが成功するかどうかは与えられた文脈で決まるとして、エージェントの作業記録を CAFE(S) の枠組みのうち Clarity（明確さ）、Actionability（実行可能性）、Fidelity（忠実さ）、Efficiency（効率）の4軸で、採点基準付きの言語モデルが1〜5点で評価する「AX（Agent Experience）」を提案した。試行した882件のセッションでは実行可能性が最も低く、評価の59.6%が3点以下（忠実さは26.6%）で、長いセッションほど点が下がった。1つのデータ分析課題に意図的に文脈の欠陥を入れて12回ずつ走らせると、どの欠陥でも欠陥のない場合よりトークンが平均91%増えた。Stack Overflow の調査では、文脈の問題を報告した回答者は AI を「とても役立つ」と評価する率が12〜28%低かった。

  • DEVCLAUDE.md や AGENTS.md の良し悪しを、エージェントの作業記録から「次に何をすればよいか分かる情報があったか」で点検できる。
  • PM文脈の欠陥はトークン費用の増加として表れる。エージェントの費用が想定より高いチームは、まず文脈の質を疑う。
出典：arXiv:2611.33480「DevEx is for Humans, AX is for Agents: Measuring Context Health in Agentic Software Work」（2026-11-24 投稿）
著者自身が探索的な結果と位置づけている。採点の妥当性確認は1人の研究者による15件の非盲検の確認のみで、欠陥の入れ方も完全には分離できていない。
コメント：コンテキスト工学の「効いているか」を、作業記録から継続的に測る道具の最初の形として注目したい。

EY 新日本、生成 AI と AI-OCR で有価証券報告書の数値チェックを強化——数千件の一次チェックが半日〜1日から1時間以内に、担当する全上場企業で運用開始

CONSULT

EY Japan が11月26日に発表した。EY 新日本有限責任監査法人の開示書類チェックツール「DiCAT」は、合計値などの計算、書類内の数値の整合性、前期書類との比較、修正前後の差分を確認する。生成 AI と AI-OCR を組み合わせ、文章中に書かれた数値も読み取ってチェックできるようにした。数千件に及ぶ数値の一次チェックにかかっていた時間は、従来の半日〜1日から1時間以内になる。11月20日から、EY 新日本が監査を担当するすべての上場企業（IFRS 適用企業を含む）で運用を始めた。対象は現在は有価証券報告書で、今後は決算短信や計算書類にも広げ、アドバイザリー業務での活用や一般企業への提供も検討する。使用しているモデル名は公表していない。

  • CONSULT監査法人側が開示書類の数値チェックに生成 AI を本番投入した。経理・開示部門のクライアントからは「自社側の作成工程にも同じことができるか」と聞かれる。表と本文の数値照合は提案しやすい題材になる。

DEVCONSULT

arXiv に11月25日に投稿された論文。エージェントのスキル（指示や資料をまとめたディレクトリ）の効果を測る SkillsBench は、人が作ったスキルで合格率が平均約16.6ポイント上がる一方、一部の課題では下がると報告している。著者は公開された7,554回の試行を1,421の組に整理し、ソースコードまで遡って監査した。効果の大きい3課題は平均74.6ポイント上がっていた（全体では18.7ポイント）が、うち2件は採点の仕組みへの依存、1件は定義の不備だった。4課題はスキルのディレクトリが空のまま、1つの実行環境は多くの試行で48の組み込みスキルを追加していた。各条件3回以下の試行では58%の組でそもそも低下を検出できず、「スキルが害になる」との結論は出せない。スキルの使い分けで2〜3ポイント上がるという結果も、ラベルを入れ替えた対照で4〜7ポイント上がり、見かけの効果だった。

  • DEVスキルを入れるかどうかは公開ベンチマークの数字でなく、自社の課題で複数回試して決める。
  • CONSULT「スキルで性能が◯%上がる」という売り文句を顧客に伝えるときは、試行回数と採点方法を確認してからにする。
