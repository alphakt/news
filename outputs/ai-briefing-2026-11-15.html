Cursor は11月13日、10月29日に公表した事案の続報を出した。攻撃者は、Cursor が推論委託先の Fireworks に発行し Fireworks 側で露出したアクセスキーを使い、データ共有用のバケットを複製した。中身は Privacy Mode を使っていないセッションのコーディングエージェント実行記録（主に2025年分）で、一部に伏せ字にされていない認証情報が含まれていた。攻撃者はそれを使って一部の SaaS や保管済みの非本番リポジトリに到達し、10月29日には盗んだ認証情報で Claude Code 拡張の改ざん版をマーケットプレイスのキャッシュに置いた。API 認証情報が露出した顧客は 0.01% 未満、実行記録が含まれた利用者は 0.05% 未満で、いずれも通知済み。

  • DEVエージェントのセッションやサポート窓口に貼った認証情報は、事業者側の記録に残り、委託先まで渡りうる。秘密はセッションに直接見せず、Privacy Mode の設定を確かめる。
  • PM通知を受けた場合は、記載された鍵をローテーションする。チーム管理者には対象の鍵の一覧が届いている。通知がなければ、該当の実行記録に自分のデータは含まれていないと Cursor は説明している。
  • CONSULT「AI ツール事業者のさらに先の委託先」が侵入経路になった実例。顧客の AI ツール選定で、再委託先・学習や記録の保持・データ共有の範囲を確認項目に入れる根拠になる。
どう試す／どう対応する：Cursor を使っているチームは、(1) Cursor からの通知メールの有無を管理者に確認、(2) 10月29日に Cursor のマーケットプレイスから Anthropic.claude-code 2.1.312／2.1.313 を導入・更新した端末がないか確認（該当すればアンインストールだけでは足りず、10月29日の告知の手順に従う）、(3) Privacy Mode が組織で強制されているかを確認する。

DEVPM

Anthropic は11月13日、Claude Platform のベストプラクティスとして常時稼働エージェントの設計記事を公開した。常時稼働といっても実際は、イベントを受けて起動し、作業して状態を保存し、また眠る「ラン」の繰り返しだとする。要素は5つ。Webhook や定期実行はエージェントを直接呼ばず、耐久性のある受信箱（DB のテーブル）に書き、受信箱ごとにワーカーは1つにする。タイマーは受信箱と分けて持つ。メモリはファイルのディレクトリとして別の保存先に置き、「調べ直せないもの」だけを残す。認証情報はエージェントの外のプロキシが付与する。利用者への連絡は送信箱にまとめ、まずは少なめにする。

  • DEV定時実行やチャット連携のエージェントを作るときの設計の型として使える。イベントの重複排除、短時間に続いたメッセージの一括処理、承認待ちでランを終えて返信で再開する「保留ツール呼び出し」が具体的に書かれている。
  • PMシステムプロンプト・ツール定義・メモリは毎回のランで読み込まれるため、ここが太るとそのまま費用になる。通知の量は評価で調整する対象だと明記されており、受け入れ基準に入れられる。
どう試す／どう対応する：いま動かしている定時エージェント（日次レポート、監視、チケット振り分けなど）を5要素に照らす。特に「同じイベントで2回走らないか」「途中で落ちたら再実行されるか」「前回何を報告したかを覚えているか」の3点を確認する。
出典：Claude「Building always-on agents」（2026-11-13）
設計の解説記事で、新しい API や製品の発表ではない。過去のセッションを見直してメモリを整理する「dreaming」は任意の工程として紹介。スケジューラは自作でも耐久実行エンジンでもよいとしている。
コメント：エージェント本体のループではなく、その外側の受信箱とタイマーが品質を決める、という整理は、PoC から運用に移る案件の設計レビューでそのまま使える。

AI Engineer Code Summit の登壇者らが「No AI Slop Manifesto」を公開——slop を「作る労力が、読み手に求める労力を下回るもの」と定義し、開示・確認・一部は必ず人が読むことを決議

PMDEV

Latent Space の11月13日付の記事によると、AIE Code Summit での議論から生まれた宣言が閉会の基調講演で紹介された。公開ページには352人の署名が並ぶ。宣言は、AI を使うこと自体は slop ではなく、品質と読み手への責任を負わずに出力を渡すことが slop だとする。巨大な PR は作る側はほぼ無料だが、レビューの費用は変わらない、という非対称も指摘する。決議は12項目で、エージェントが書いたものは開示し、重要な部分は送る前に確かめる。AI レビューやリンターは役立つが十分ではなく、重要度に応じて一部は人が見る。成果はコード行数、マージした PR 数、使ったトークン数ではなく、何が出荷され誰の役に立ったかで測る。

  • PM「PR 数」「トークン消費」を生産性指標にしない、という主張を、実務者の連名という形で引用できる。チームのレビュー規約を書くときの叩き台になる。
  • DEVコードを全部は読まなくなっても、計画・設計・結果のどれかは読み続ける、という線引きが示されている。slop を受け取ったら送り手に伝えて見直しを頼む、も決議に入っている。
出典：The No AI Slop Manifesto（全文と署名）Latent Space「[AINews] The No AI Slop Manifesto」（2026-11-13）
宣言のページ自体には公開日の記載がなく、日付は関係者（swyx 氏）による Latent Space の記事に基づく。署名者の所属は記載なし。宣言は「誰も完全には分かっておらず、唯一の正解はない」と結んでいる。測定や事例を伴う報告ではない。
コメント：昨日号の slop PR 実態調査が「受け取る側の現状」なら、こちらは「出す側の約束」。両方をそろえるとレビュー規約の議論がしやすい。

CONSULT

SCSK は11月13日、専門商社・卸売業向けの AI エージェントを同日から提供すると発表した。構成は4つのエージェントと、共通で参照するデータ・ナレッジ基盤。営業・提案支援は顧客、商談、仕入先の在庫や納期を横断して集め、提案の仮説と次の行動を示し、面談メモの要約を SFA に反映する。見積・取引支援は形式の異なる見積依頼を読み取り、在庫・単価・納期・与信・取引実績と照合して、見積書の下書きから承認依頼までを支援する。SCSK は CRM／SFA や ERP との連携、業務プロセスの見直し、運用の定着まで伴走するとしている。

  • CONSULT国内 SIer が「業種×業務」単位でエージェントをパッケージ化し、システム連携と定着支援を一体で売る動きの一例。商社・卸の顧客から比較を求められたときは、使うモデル、価格、導入実績が発表文にない点を確認事項として挙げられる。
出典：SCSK プレスリリース「『専門商社向けAIエージェント』を提供開始」（2026-11-13）
基盤モデル、価格、導入実績、効果の目標値は発表文に記載なし。背景として、顧客対応で複数システムや他部署への確認が要る営業担当者が 63.8% という同社調査を挙げている。今後は契約更新・保守、物流・在庫アラート、与信リスクチェックなどへ広げる計画。

DEV

Zenn の検証記事（11月14日）は、MCP の HTTP 接続でツールの応答前に通信を切ったとき、ツールが二重に実行されるかを自作サーバーで調べた。環境は Claude Code 2.1.316、同一マシン上の平文 HTTP。ツールに1行書き込む副作用を持たせ、同じ JSON-RPC の id が二度届くかで再送を判定した。「1回だけ呼んで」と指示した17回はすべて副作用が1行で、全34実行で同一 id の重複は0件だった。回数の指示を外した3回では副作用が2行になったが、id が別だったため、再送ではなくモデルが呼び直したものと著者は判断している。応答ヘッダを流す前に切ると数秒でエラーになり、流した後に切ると約60秒後にタイムアウトが届いた。

  • DEV二重実行の原因は通信層の再送より、モデルの「呼び直し」のほうにある。書き込み系の MCP ツールにはべき等キーを持たせ、サーバー側のログに呼び出しの通し番号を残す。終了コードでは切断とツール側のエラーを区別できない。
出典：Zenn「MCPの道具呼び出しを応答前に切断しても、二重に届いた回は34回中0件。切断点をずらすと60秒待たされた」（2026-11-14）
個人による検証で、試行は34回。著者は、再送が起きる条件は見つかっていないこと、外部ネットワーク、HTTPS、他のバージョンやモデルでは試していないことを明記している。
コメント：規模は小さいが、「副作用の回数」と「呼び出しの id」を分けて数える切り分け方は、MCP サーバーの障害調査でそのまま真似できる。
