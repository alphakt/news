カカクコムの CTO らが11月26日のアーキテクチャConference 2026で発表し、27日に資料を公開した。C# 約800万行と Classic ASP 約160万行を Python と FastAPI で作り直す計画で、5段階×3層・110体のエージェントが現行コードから仕様を抜き出し、設計と実装まで行う。画面の約7割が一連の処理を終え、完了予定は2027年5月から9月に延びた。社内システム1つで比べると、Opus 5.5 の自律エージェント型は外部の評価役の65項目をすべて満たし、約4時間・約196ドルで済んだ。仕様書から作るワークフロー型（Opus 4.6）は32項目で、約66時間・約2,123ドルかかった。ただし Opus 5.5 を全体に使うと API 費用が1.4〜2倍になり、数日で元に戻した。プロンプトは約7.5万行から約12万行に増え、6月に入れた5つの対策のうち3つは外した。

  • CONSULT大規模なレガシー刷新を AI で進める国内の実例として、費用・期間・失敗まで数字で示せる。刷新を検討する顧客への提案資料に引用できる。

電通総研のテックブログが11月27日に公開した。エージェントは Docker Sandboxes の microVM で動かし、認証情報は VM に置かず、ホスト側のプロキシが許可した宛先への通信にだけトークンを付ける。AGENTS.md は詳細な仕様でなく「地図」として短く保ち、定型作業はスキルに分ける。テストやビルドの長い出力はログファイルに逃がし、会話には成否と所要時間、失敗時の末尾だけを返す。守らせたい約束は文章でなくフックや依存関係の検査で機械的に止め、違反メッセージに正しい置き場所を書く。検証は、高速な lint・テスト、プロパティベーステスト、差分だけのミューテーションテスト（合否には使わない）、別系統のモデルによる反証の4層。導入は隔離から始める順序も示した。

CONSULTPM

あずさ監査法人と KPMG コンサルティングが11月27日に発表した。部門ごとにエージェントを作った結果、シャドー AI、責任者や権限のあいまいさ、費用の把握不足が起きているとして、エージェント共通のリスクから統制の要件を決め、標準の構成や共通基盤に組み込む支援を行う。あわせて、主要なクラウド事業者の統制機能では見えない部分を補う「追加の統制レイヤー」を製品として提供し、事業者の外にあるエージェントの管理や、エージェントの行為ごとの監視・異常検知を行う。背景として、シャドー AI による不適切なデータへのアクセスや、自律型 AI による誤ったデータ削除の事例を挙げた。価格や効果の数値は公表していない。

コンテキストの圧縮を基盤任せにせず、モデル自身に決めさせると精度が上がる——32K トークンの制限下で GPT 6.1 の正答率が21%から56%に

DEV

arXiv に11月25日に投稿され、27日に公開された論文。今のエージェント基盤は、コンテキストが一杯になると基盤側が履歴を要約して縮める。著者らは、いつ何を縮めるかをモデル自身が API を通じて決める方式を NVIDIA のオープンソースのエージェント基盤に組み込み、文書調査と機械学習の作業で、8K から512K トークンまでの制限で比べた。API をうまく使えるモデルは、特に制限が厳しいときに少ない入力で精度が上がった。GPT 6.1 は OfficeQA Pro v2 で32K の制限下の正答率が21%から56%になり、Kimi は入力トークンを最大41%減らしながら精度を上げた。モデルごとに縮める頻度や時期が違い、プロンプトで時期が変わる。推論エンジンが変更のない部分のキャッシュを再利用すると、計算を最大15%減らせた。

  • DEV長い作業でコンテキストが足りなくなるエージェントは、自動要約に任せるより「何を残すかをモデルに決めさせる」道具を渡すほうが効く場合がある。プロンプトで圧縮の時期が変わる点も設計に入れる。
出典：arXiv:2611.34147「Letting Models Manage Their Own Context: Where We Stand」（2026-11-25 投稿）
効果はモデルによって差が大きく、API を使いこなせるモデルでのみ上がる。
コメント：コンテキスト工学の担い手が人や基盤からモデル自身に移る流れを、数字で示した最初のまとまった比較として追いたい。

Thoughtworks「AI 導入は一度に作り替えず、1スプリントずつの実験で」——レビューの詰まりに AI レビューを試したが雑音が増えただけで、ペアプログラミングに切り替えた例

PM

Thoughtworks のブログに11月27日、Moritz Wilke 氏が寄稿した（会社の公式見解ではないと注記）。AI はチームが元々持っている開発の習慣を増幅するため、ツールを足す前に、作業が本番に届くまでの流れを書き出し、最も詰まっている1か所とその上流の原因を選び、1スプリントだけ1つの対策を試して振り返る、を繰り返すよう勧める。例では、レビューの詰まりに対して PR を500行までに制限し、lint を CI で自動化し、AI に設計やインターフェースのテストの土台を作らせた。AI レビューのエージェントも試したが、雑音が増えるだけでレビューは速くならず、やめてペアプログラミングに移った。AI はテストやパイプラインを作る費用を下げるために使うべきだとしている。

  • PMAI ツールの導入計画は「詰まっている1か所に1スプリントの実験」の単位で組むと、外れても戻しやすく、現場の抵抗も小さい。
出典：Thoughtworks「Refactoring the Engine: An Incremental Path to AI-Assisted Delivery」（2026-11-27）
