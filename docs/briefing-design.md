# AI最新動向簡報 — 編集方針（v2, 2026-10-02）

この文書は日次簡報の「何を・誰のために・どう選ぶか」を定める。生成 prompt（`docs/briefing-prompt.md`）と
運用規約（`CLAUDE.md`）はこの方針に従う。方針を変えるときはまずここを直す。

## 1. 目的

alphakt（日本の AI/IT コンサルティング）の実務に**使える**情報だけを毎日届ける。
「業界ニュースの消化」ではなく、「明日の仕事のやり方・提案内容・判断」が変わる情報を選ぶ。

## 2. 読者の 3 視点（1 本の記事が複数に当たってよい）

| タグ | 読者 | 関心 | 典型例 |
|---|---|---|---|
| **DEV** | 開発者 | AI ネイティブな開発の仕方、コンテキスト工学（CLAUDE.md / AGENTS.md / SOUL.md / DESIGN.md / skills）、エージェント基盤（決定モデル、MCP、ゲートウェイ、評価）、AI 生成 PR の人間レビュー、知識の蓄積（LLM が維持する wiki / RAG） | AGENTS.md の効果を測った研究、エージェントの判断を小さなモデルに任せる設計、レビュー門番の実装例 |
| **CONSULT** | コンサルタント | 来週クライアントに聞かれること：企業導入の事例と失敗、価格・提供条件・可用性の変化、提案に組み込める方法論、競合（SIer / Big4 / クラウド各社）の新サービス、**日本国内**の規制・ガイドライン | 業種別エージェント導入事例、モデルの提供停止や価格改定、経産省・IPA・個人情報保護委員会の新指針、国内 SIer の AI 新サービス |
| **PM** | プロジェクト管理者 | AI がプロジェクトの見積・分担・品質・コストをどう変えるか | AI がコードを書いた後にレビューが詰まる実データ、トークン費用の統制、エージェント権限・監査の実践、DORA / Thoughtworks Radar 類の報告 |

各記事には当たった視点のタグを付け、**視点ごとに「だから何か（So what）」を 1 文**書く。
3 視点のどれにも So what が書けない記事は載せない。

## 3. 収録基準

### 3.1 載せるもの
- 直近 48 時間以内に公開・更新されたもの（一次情報の日付で判断）。
- 一次情報に遡れるもの（公式ブログ、リリースノート、論文、官公庁、当事者の投稿）。二次記事は手がかりとしてのみ使い、出典には一次情報を置く。
- 上記 3 視点のいずれかに So what が書けるもの。

### 3.2 載せないもの（既定で除外）
- 資金調達・評価額・株価・IPO。**例外**：モデルやサービスの可用性・価格・提供条件が変わる場合のみ。
- 「X vs Y」「ベスト 10」などの比較記事・まとめ記事（手がかりにはしてよい）。
- 一次情報に辿れない噂・リーク。
- 既に `seen.json` にある URL / 同一事象。

### 3.3 政策・規制の基準：「AI 従業者が知らないと恥ずかしい」
次を**すべて**満たすものだけ収録する。
1. 署名・成立・施行済み、または主要官庁の正式な公表（提案段階・観測記事は除外）。
2. モデルの可用性、データの越境、責任の所在、調達・契約の要件のいずれかに影響する。
3. 管轄が日本・米国・EU・中国のいずれか。日本は優先度を上げる（クライアントが日本企業のため）。

## 4. 情報の集め方（4 層）

**第 1 層：固定源池（`sources.json`）**
毎日必ず走査する一次源。`scripts/collect.py` が feed を一括取得し、直近 48h の記事を lens 別に書き出す。
feed のない源（`pages`）は WebFetch で確認する。源は**この環境で実際に本文を取得できたもの**だけを登録する
（取得不能なものは `unreachable` に理由付きで残す）。

**第 2 層：主題プローブ（WebSearch）**
製品名ではなく主題で検索する。製品は入れ替わるが主題は安定しているため、新しいものが自然に浮かぶ。
主題の例（適宜更新）：
- human review of AI-generated code / AI PR review gate
- context engineering / AGENTS.md / CLAUDE.md / DESIGN.md / agent skills
- agent governance enterprise / agent permissions audit
- LLM-maintained wiki / agentic knowledge base
- AI コーディング 導入事例 / 生成AI ガイドライン 改定 / エージェント 業務導入 事例
- 経産省 AI / 個人情報保護委員会 生成AI / IPA AI セキュリティ

**第 3 層：候補プール（`candidates.json`）**
第 1・2 層に現れた製品・概念・手法の名前を記録する（初出日、出現回数、独立した出典数、最終出現日）。
固定の watchlist は持たない。**関心対象に昇格する条件**（いずれか）：
- 7 日以内に独立した 2 出典以上で言及。
- 一次実践者（企業の技術ブログ、著名開発者）が「使っている」と書いた。
- 主要ベンダーが採用・統合した。
30 日間言及がなければ自動で退出。種（seed）として与えられた名前も同じ規則で扱う。

**第 4 層：編集判断（採点）**
候補ごとに 4 項目を 0–2 で採点し、合計 5 以上を収録候補とする。
| 項目 | 0 | 1 | 2 |
|---|---|---|---|
| 仕事の仕方が変わるか | 変わらない | 一部の人・場面で | 多くの人の既定が変わる |
| クライアントが聞いてくるか | 聞かない | 一部業種で | ほぼ確実に聞かれる |
| 一次証拠の強さ | 二次情報のみ | 一次情報あり | 一次情報＋実測・事例 |
| 新鮮さ | 48h 超 | 24–48h | 24h 以内 |

## 5. 出力の構成

- 重要度ラベルは**行動可能性**で決める。
  - **高**：今すぐ試せる／今すぐ対応が要る。必ず「どう試すか／どう対応するか」を 1 行添える。
  - **中**：追跡する価値がある。
  - **低**：知っておけばよい。
- 各記事：見出し（1 文）／本文 200–300 字／出典（一次情報、クリック可能）／視点タグと So what／編集コメント 1 文。
- 末尾に **候補プールの動き**（新規・昇格・退出）を 1–3 行。
- 動きのない日は、関心対象の 1 つを**深読み**する（解決する課題／使い方／代替との比較）。件数を埋めるための収録はしない。
- 件数は 3–6 件を目安。多い日でも 8 件まで。

## 6. 品質確認（毎回）
- 出典 URL は実際に取得して本文を確認したものだけ。取得できなかったものは載せない。
- 日付は一次情報の日付で 48h 以内か確認。
- `seen.json` に収録分を追記。`candidates.json` を更新。
- 生成物が `main` にあることを確認（`CLAUDE.md` の手順）。

## 7. トークン予算（2026-10-06 追加）

初回ラン（10/6 号）の実績: WebFetch 144 回、WebSearch 59 回、約 55〜60 万トークン。
主因は (a) 3 体のサブエージェントが同じ収集結果を再読した、(b) feed のないページ 23 件を毎回 WebFetch した
（ほぼ全て変化なし）、(c) メインとサブエージェントが同じ URL を重複取得した、の 3 つ。

対策（実装済み）:
- `scripts/collect.py` が pages のリンク一覧を `state/page-snapshots.json` と比較し、新規リンクだけを出す。
  変化のないページは 1 行で済み、WebFetch しない。
- 出力は要約 90 字まで、feed ごとに上限、`seen.json` 済みは除外。1 回の収集結果は 5 万字以内を目安。
- 分視点のサブエージェントは使わない。収集結果を 1 回読んで候補 ≤12 件を決め、その URL だけ検証する。

1 ランの上限: **WebFetch ≤ 15、WebSearch ≤ 8、サブエージェント ≤ 1、合計 ≤ 15 万トークン**を目安。
超えた場合は範囲を広げず、手元の材料で定稿する。

## 8. 日付規則の確認
一次情報の公開日が 48 時間以内であることが収録条件。二次報道が新しくても一次が古ければ載せない（例外なし）。
